# Conditional logic: IF, IFS, SWITCH, AND, OR

`IF` was a sneak preview in lesson 1.3. The full story is bigger: nested `IF`s collapse fast under their own weight, `IFS` cleans them up, `SWITCH` handles equality matches, and `AND`/`OR`/`NOT` compose any condition you can describe in words. This lesson covers the full vocabulary using the everyday adtech case: bucketing campaigns by ROI and translating platform names into categories.

The progression matters because almost every dashboard formula past a certain complexity is conditional logic in disguise. "Scale candidate" labels, ROI tier buckets, platform-to-category translations, "pause if losing and below threshold" decisions: each is a conditional with a particular shape. Pick the wrong shape (nested `IF` for what should be `IFS`, `IF` chain for what should be `SWITCH`) and the formula gets unreadable; pick the right shape and a four-line conditional reads like a single thought.

## Nested IF: where it breaks

You can nest one `IF` inside another's value-if-false slot to build a chain. Two buckets: easy. Five buckets: a parenthesis-counting nightmare. Compare the same logic: assign each campaign a performance label based on ROI:

{`=IF(F2/E2>=2,"Star",
  IF(F2/E2>=1.2,"Profitable",
    IF(F2/E2>=0.9,"Break-even",
      "Loss")))`}

  </ComparePanel>
  <ComparePanel label="IFS: linear, scannable" tone="positive">

{`=IFS(F2/E2>=2,"Star",
     F2/E2>=1.2,"Profitable",
     F2/E2>=0.9,"Break-even",
     TRUE,"Loss")`}
    </pre>

Both formulas grade the first campaign (ROI = 487.30/342.18 ≈ 1.42) as `Profitable`. The right-hand version is easier to write, easier to read, and easier to modify. The trailing `TRUE, "Loss"` is the "default" branch: `TRUE` always matches, so it's the catch-all for anything that didn't hit an earlier condition.

## IFS: condition, value, condition, value...

`IFS` takes pairs: a condition and a value, repeated. It returns the value of the **first** condition that's true. If none match, it returns `#N/A`. Always end with a `TRUE` catch-all to avoid that. The full signature and parameter table:

<TryIt
  data={CAMPAIGNS}
  inputCell="H2"
  expectedFormula='=IFS(F2/E2>=2,"Star",F2/E2>=1.2,"Profitable",F2/E2>=0.9,"Break-even",TRUE,"Loss")'
  task={<>Bucket the first campaign's ROI: <code>Star</code> if ROI ≥ 2, <code>Profitable</code> if ≥ 1.2, <code>Break-even</code> if ≥ 0.9, otherwise <code>Loss</code>. The result should be <code>Profitable</code>.</>}
  hint={<>Four condition-value pairs. The condition is <code>F2/E2 {">"}= ...</code> for each threshold. End with <code>TRUE, "Loss"</code> as the catch-all.</>}
  answer={<>IFS evaluates conditions left-to-right and returns the value paired with the first true one. Order matters: <code>F2/E2 {">"}= 0.9</code> is true for the first campaign (ROI ≈ 1.42), but it's not the first match: <code>F2/E2 {">"}= 1.2</code> is also true and earlier in the list. The order needs to go from strictest to loosest. The <code>TRUE</code> catch-all guarantees a match for any input that didn't hit an earlier rule. In real adtech work, ROI buckets like this drive scaling decisions: Stars get more budget, Losses get paused.</>}
/>

## SWITCH: equality matches

`SWITCH` is `IFS` for equality checks. Pass an expression, then alternate match-and-return pairs, with an optional default at the end. The trade with `IFS`: `SWITCH` is dramatically shorter when every branch is an equality check, but it cannot do thresholds or ranges. Reach for `SWITCH` when the expression is a discrete code (platform name, status enum, region code) and for `IFS` when the branches are comparisons.

The classic adtech use: translate platform names into broader categories so dashboards can show "Native vs. Social vs. Search" totals without listing each platform individually.

<TryIt

  task={<>Translate the first campaign's platform (Google) into a broader category. Use SWITCH with these pairs: Taboola/Outbrain/MediaGo/Poppin → Native; Facebook/TikTok → Social; Google → Search; default → Other. The result should be <code>Search</code>.</>}
  hint={<>The first argument is the value being compared (D2). Then pairs of platform-name and category. The last lone argument is the default for anything that didn't match.</>}
  answer={<>SWITCH only handles equality: you can't write <code>{">"}=80</code> in a SWITCH branch. For range checks like ROI buckets, use IFS. SWITCH shines for discrete-value translations: platform → category, status code → label, region → manager, currency → conversion rate. The default catches any new platform that gets added later (so the formula doesn't return <code>#N/A</code> when an unknown name shows up via IMPORTRANGE). In production, the platform-to-category map often lives in a separate "Config" sheet and gets pulled in via XLOOKUP: same idea as SWITCH but data-driven.</>}
/>

## How to choose

| Pattern | Use |
|---|---|
| Single yes/no | `IF(condition, yes, no)` |
| 3+ ranked thresholds | `IFS(cond1, val1, cond2, val2, ..., TRUE, default)` |
| Discrete value lookup | `SWITCH(expr, match1, val1, ..., default)` or `XLOOKUP` against a config table |
| Combine multiple conditions | `AND(...)`, `OR(...)`, or nest them |
| Negate a condition | `NOT(...)` or just flip the comparison |

Once you have IFS in your toolbox, you'll rarely write more than two nested IFs again. Once you have SWITCH, IFS-with-equality stops being a thing. And once a SWITCH grows past ~10 branches, move it to a config table and use XLOOKUP: easier to maintain when the team adds new platforms or verticals.

## Used in the wild

In the team's actual workbooks:

- **ROI buckets drive scaling decisions.** An IFS column tags each campaign as Star/Profitable/Break-even/Loss. The dashboard then SUMIFS spend by bucket to show "how much of our budget is on Stars vs. Losses".
- **Platform → category SWITCH/XLOOKUP feeds the Native/Social/Search totals row** in every dashboard.
- **AND-conditions on multiple metrics drive the "scale candidate" / "pause candidate" lists.** Combining ROI threshold AND spend threshold AND date-range filter is the typical shape.

## Pro pitfalls

- **`#N/A` from IFS** means none of your conditions matched. Always end with `TRUE, default_value`.
- **`#N/A` from SWITCH** means no match and no default supplied. Always pass a default as the last argument.
- **Order matters in IFS.** Strictest condition first, loosest last (or use `TRUE` catch-all). Reversed order silently returns the wrong bucket.
- **Comparing imported text to a number** does not error but always returns FALSE. If revenue comes in via IMPORTRANGE as a string ("487.30" not 487.30), `F2 > E2` never matches. Coerce with `VALUE(F2)` or `F2*1`.
- **`AND` and `OR` short-circuit differently inside `ARRAYFORMULA`.** Per-row, `AND(A2:A, B2:B)` reduces to a single scalar (all rows combined), not a per-row array. For per-row boolean arrays, use `*` (AND) and `+` (OR) between the conditions; lesson 1.10 covers the boolean-arithmetic trick when it introduces ARRAYFORMULA, and lesson 1.14 revisits it for FILTER.
- **SWITCH growing past ~10 branches becomes unmaintainable.** Move it to a config sheet and `XLOOKUP` against the map. The mapping then becomes data, not code, and non-coders can edit it.
