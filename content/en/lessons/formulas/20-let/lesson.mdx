# LET: name intermediate values inside a formula

`LET` lets you assign names to values inside a single formula. The names exist only within the `LET`: they are not on the sheet, they are not in the workbook namespace, they are scoped to the one cell. Read the formula and you read the names; close the cell and they vanish.

The reason to care is twofold. First, complex formulas become readable: instead of `=(F2-E2-G2*0.05)/F2` you write `LET(rev, F2, fee, G2*0.05, profit, rev - E2 - fee, profit / rev)` and a reader scans names instead of decoding arithmetic. Second, slow formulas become fast: when the same subexpression appears five times, `LET` lets you compute it once and reference it by name. Sheets evaluates each binding once, even if the body references it many times. On `IMPORTRANGE`-heavy dashboards this is the difference between a dashboard that recalculates in 1 second and one that takes 8.

## Syntax

```
LET(name1, value1, name2, value2, ..., body)
```

You alternate name/value pairs, then end with the body: the expression that uses the names. The body is the only required final argument; everything before it comes in pairs.

A later binding can use an earlier one, which is how you build pipelines. The body must be exactly one expression (no semicolons, no statements). If you need internal structure, nest another `LET` inside.

## Why LET matters: avoiding "spreadsheet stew"

Without `LET`, complex per-row formulas turn into nested unreadable strings:

```
=IF((F2-E2)/E2>0.5, "Scale", IF((F2-E2)/E2>0, "Hold", IF((F2-E2)/E2>-0.2, "Watch", "Kill")))
```

The same `(F2-E2)/E2` is written four times. Sheets optimizes the computation, but the reader still sees the noise, and changing the ROI definition (say, subtracting a fee) means hunting all four copies.

With `LET`:

```
=LET(
  roi, (F2 - E2) / E2,
  IF(roi > 0.5, "Scale",
   IF(roi > 0, "Hold",
   IF(roi > -0.2, "Watch", "Kill")))
)
```

`roi` is computed once, used four times, and named. Adding the fee is a one-character edit in the binding.

## LET binds in order: pipelines

A later binding can use earlier ones. This is how you build derivation chains:

```
=LET(
  spend, SUM(E2:E13),
  revenue, SUM(F2:F13),
  profit, revenue - spend,
  roi, profit / spend,
  IF(roi > 0.3, "Strong period", "Weak period")
)
```

Five steps, each named, each reusable, each computed in terms of earlier ones. The reader sees the logic top-down: get spend, get revenue, derive profit, derive ROI, decide. The same logic without `LET` is one giant arithmetic expression that nobody (including the author six months later) wants to debug.

## LET for performance

If the same expensive subexpression appears multiple times, `LET` avoids re-computing it. This matters most when the subexpression is a slow `QUERY`, an `IMPORTRANGE`, or a large array operation.

```
=LET(
  data, QUERY(IMPORTRANGE("...", "raw!A:F"), "SELECT * WHERE Col2 = 'Yoav Cohen'", 1),
  rows, ROWS(data),
  total, SUM(QUERY(data, "SELECT Col6", 0)),
  rows & " campaigns, " & TEXT(total, "$#,##0") & " revenue"
)
```

`data` (the slow `IMPORTRANGE`+`QUERY`) is computed once. Without `LET`, the import runs twice (once for `ROWS`, once for `SUM`) and you pay the network round-trip both times. On a dashboard that derives ten metrics from one source, the savings compound, and you stay under the `IMPORTRANGE` traffic cap that otherwise turns the whole workbook into `#REF!`s by mid-afternoon.

## Used in the wild

- **KPI calculators** that take a buyer + period and return a verdict. `LET(spend, ..., revenue, ..., roi, ..., verdict, IF(...))`.
- **Dashboard summary cells** that compute period-over-period changes. Bind `current` and `previous`, then derive `delta` and `pct_change`.
- **`IMPORTRANGE`-heavy dashboards.** Bind the imported data once at the top of the `LET`; reference it as many times as needed in the body. Cuts response time in half on slow imports (lesson 1.27 covers the broader IMPORTRANGE patterns).
- **Inside `LAMBDA`.** Any non-trivial `LAMBDA` body uses `LET` to break the calculation into named steps. The combination is what makes named functions (lesson 1.21) readable.
- **Conditional summaries.** Bind a filtered subset once, then compute multiple statistics over it (count, sum, average) without re-filtering.

## Pro pitfalls

- **Names cannot shadow built-in functions.** `LET(SUM, 5, SUM)` errors. Pick names like `total`, `spend_total`, `s` instead.
- **Names are case-insensitive but display as-typed.** `LET(Roi, 0.5, ROI)` works but reads weirdly. Pick a casing convention (lowercase is most common) and stick to it.
- **The body must be exactly one expression.** No semicolons, no statements. If you need multiple things, return them in an array or nest another `LET`.
- **Bindings are eagerly evaluated.** `LET(x, slow_function(), 0)` still pays the cost of `slow_function()` even though the body never uses `x`. Only bind values you will actually use.
- **Forward references do not work.** A binding can use earlier names, never later ones. Order bindings in derivation order.
- **`LET` inside `LAMBDA` is fine, and useful.** A `LAMBDA`'s body must be one expression. `LET` is the standard way to give that expression internal structure.
- **Do not over-name.** A 3-line `LET` with 8 bindings, half of which are used once, is harder to read than the inline form. Use `LET` when names buy clarity, not because you have heard you should use `LET`.
- **`LET` does not memoize across cells.** Bindings live for one formula evaluation in one cell. If two cells share the same expensive subexpression, hoist it into a single helper cell that both reference.
