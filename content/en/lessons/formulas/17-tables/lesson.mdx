# Tables: structured ranges that don't break

A **Table** is a Sheets feature that turns a range into a structured object: it gets a name, typed columns, alternating-row formatting, and self-extending bounds. Once data is in a table, you stop saying "the cells from `E2` to `E1000`" and start saying `Campaigns[Spend]`. When a new campaign is pasted at the bottom, every formula, chart, and pivot that references the table picks it up automatically. No `$E$2:$E$1000` "extend the range now and hope it covers tomorrow's rows."

This is the single biggest readability and robustness upgrade Sheets has shipped in years, and the team's master campaign log is exactly the kind of data that should live in one. The lesson walks through the conceptual model, the structured-reference syntax, the workflow gotchas (especially the Excel-isms that *don't* carry over), and the patterns that turn a brittle "growing log" into something the whole dashboard layer can lean on safely.

## What a table looks like

When you convert a range, Sheets wraps it in a visual frame: bold header row, alternating-row striping, a small table-name dropdown at the top-left, and per-column type dropdowns in each header cell. The data underneath looks like any other range, but Sheets now treats it as a single object with a name.

## Convert a range into a table

The workflow is short:

1. Select the range, or click any cell in the data (Sheets detects the bounds).
2. **Format → Convert to table** (or right-click → "Convert to table").
3. Sheets infers column types (text, number, currency, date, percent), applies formatting, and gives the table an auto-name like `Table1`.
4. Click the table-name dropdown at the top-left to rename it to something meaningful: `Campaigns`, `Buyers`, `Verticals`.

The fourth step is non-optional. `Table1` is meaningless and every formula reads worse for it.

## Structured reference syntax

Once a range is a table named `Campaigns` with columns `Date | Buyer | Vertical | Platform | Spend | Revenue`, every formula can reference it by name:

| Reference | Means |
|---|---|
| `Campaigns[Spend]` | The whole Spend column (data only, no header) |
| `Campaigns[#HEADERS]` | The header row |
| `Campaigns[#DATA]` | All data rows, all columns (synonym for the table body) |
| `Campaigns[#ALL]` | Header + data + totals |
| `Campaigns[#TOTALS]` | The totals row, if one exists |
| `Campaigns[[#HEADERS],[Spend]]` | Just the header cell of the Spend column |
| `Campaigns[[#ALL],[Spend]]` | The Spend column including its header |

The plain `Campaigns[Spend]` form is the one you reach for 95% of the time. Reserve the `#HEADERS`, `#ALL`, `#TOTALS` variants for the cases where you genuinely need the header text or totals row pulled in.

## The sandbox caveat

The interactive **TryIt** examples on this page run inside a sandboxed formula engine that does not understand Sheets tables. So the in-lesson cells use ordinary range references like `E2:E13`. When you click **Start lesson** to provision a real sheet, you will write the structured-reference forms (`Campaigns[Spend]`) against an actual table and see how they auto-extend.

Read the two versions side by side as you scan the page: the range form is what you type here, the table form is what you type in production.

## When tables shine, when they don't

Tables earn their place for any data that has a recognizable schema and that grows over time:

- **Master logs.** Campaign logs, order logs, error logs, anything append-only.
- **Lookup references.** A `Verticals` table with vertical → category → benchmark CPC. Adding a new vertical is one row; downstream `VLOOKUP`s pick it up.
- **Dashboard sources.** Pivot tables, charts, and `SUMIFS` aggregations all benefit from naming.

Tables are *not* the right shape for:

- **Sparse pivot-style grids** where the column count varies. Tables expect a stable column schema.
- **Free-form scratch sheets** with no consistent header row.
- **Data that lives in another workbook** and arrives via `IMPORTRANGE`. The imported copy is plain values; the source's table-ness does not carry across the workbook boundary.

## Used in the wild

- **Master campaign log as a table.** The team's main campaign sheet becomes `Campaigns`. Every dashboard pivot, `SUMIFS`, and chart references `Campaigns[Revenue]` instead of `Sheet1!F:F`. Pasted-in rows flow into every downstream formula automatically.
- **Verticals lookup table.** A small table with vertical → category → benchmark CPC. Lookup formulas read `=VLOOKUP(B2, Verticals[#ALL], 2, FALSE)` and survive new-vertical additions without edits.
- **Per-buyer dashboards.** `=SUMIFS(Campaigns[Spend], Campaigns[Buyer], $A2)` filled across Yoav, Maya, Ben, Dina, Roni: readable and stable.
- **Chart sources.** Point a chart at `Campaigns[Date]` and `Campaigns[Revenue]`. The chart updates as the table grows; no need to re-edit chart ranges every Friday.
- **Conditional formatting with structured refs.** Rules like "highlight rows where Revenue < Spend" written against `Campaigns[Revenue]` and `Campaigns[Spend]` extend with the data automatically.
- **Paste-and-convert to table with Gemini (April 2026).** When you paste unstructured text into a sheet (a bullet list, freeform notes, a JSON dump from a partner), Sheets now surfaces a **Convert to table** prompt powered by Gemini ([Workspace Updates, April 2026](https://workspaceupdates.googleblog.com/2026/04/paste-and-convert-unformatted-text-into-Google-Sheets-tables-with-Gemini.html)). Click it and Gemini infers headers, splits fields, and writes a proper table you can name, type, and reference with structured syntax. The team uses this when a buyer pastes the previous week's results from Slack and the rows arrive as one wall of text. Track 5 covers the Gemini-in-Sheets surface in depth: lesson 5.3 (Fill with Gemini) is the closest cousin, and lesson 5.4 (build-and-edit side panel) is the next step up. Same review discipline applies in both directions: read what Gemini produced before you point a dashboard at it.

## Pro pitfalls

- **No `[@col]` current-row syntax.** Per-row formulas inside a table use plain cell references (`=E2*1.1`), not `=[@Spend]*1.1`. Excel-trained users get this wrong constantly.
- **Spaces in table names become underscores in formulas.** A table named "Car Deals" is `Car_Deals[Spend]`, not `'Car Deals'[Spend]` or `Car Deals[Spend]`. The team usually avoids spaces entirely.
- **Tables don't carry through `IMPORTRANGE`.** A table in workbook A becomes plain values when imported into workbook B. Either convert the imported range to a new local table in B, or operate on the import with `QUERY` (lesson 1.12).
- **Column type inference can mis-read.** One stray text entry in a "Date" column makes Sheets infer the whole column as text. Fix the source data, then set the column type explicitly from the header dropdown.
- **You can't easily un-table.** "Convert back to range" exists in the table dropdown but it strips formatting and column types. Plan the table boundaries deliberately before converting.
- **Sorting inside a table reorders the physical rows.** From outside, `Campaigns[Revenue]` returns the values in current physical order. Usually fine, occasionally surprising when a teammate sorts the table for a one-off scan and forgets.
- **Adding a column at the edge auto-extends the table, but adding a column outside the table does not extend it.** New columns to the right are picked up if Sheets detects them as part of the schema. To force inclusion, drag the table's resize handle or use **Format → Resize table**.
- **Conditional formatting on plain ranges does not auto-extend.** If your CF rule is on `F2:F1000` rather than `Campaigns[Revenue]`, new rows past row 1000 are unstyled. Tables fix this *only* if the CF rule was written against the structured reference.
