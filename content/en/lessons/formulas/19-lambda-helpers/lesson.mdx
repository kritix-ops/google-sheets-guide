# MAP, REDUCE, SCAN, BYROW, BYCOL, MAKEARRAY

These six functions are what `LAMBDA` (lesson 1.18) actually exists for. Each one takes a LAMBDA and applies it across an array in a specific shape: cell by cell (`MAP`), folded into one value (`REDUCE`), folded with intermediate steps preserved (`SCAN`), once per row (`BYROW`), once per column (`BYCOL`), or generated from nothing (`MAKEARRAY`). Together they replace every "drag this formula down 1000 rows" workflow with a single cell that emits the whole transformation.

In adtech terms: every per-row KPI column, every weighted aggregate, every running cumulative spend chart, every per-campaign summary across a wide pivot. Those are the building blocks of the whole calculated-column shelf. The lesson covers all six, with the focus weighted toward `MAP`, `REDUCE`, and `SCAN` because those carry the most pedagogical load. `BYROW`/`BYCOL` are short variants of the same idea; `MAKEARRAY` got its full canonical introduction in lesson 1.11.

## MAP: apply a LAMBDA to every cell

`MAP(array1, [array2, ...], lambda)` returns a new array the same shape as the inputs, where each cell is the LAMBDA applied to the corresponding position in the input arrays. With one array, the LAMBDA takes one parameter; with two arrays, two parameters; and so on.

Reach for `MAP` whenever you would otherwise write a formula in row 2 and drag it down. The point is exactly that: one cell, one formula, the whole transformation. New rows in the source extend the output automatically when paired with open-ended ranges.

Four prices. Apply a 10% markup to every row. One formula in `D2` spills the four marked-up values.

## REDUCE: fold an array into a single value

`REDUCE(initial_value, array, LAMBDA(accumulator, current, body))` walks the array left-to-right, threading an *accumulator* through your LAMBDA. The accumulator starts at `initial_value` and updates on each step; the function returns the final accumulator after the array is exhausted.

`REDUCE` is the most general aggregation tool in Sheets. `SUM`, `COUNT`, `AVERAGE`, `MAX`, `MIN`, `SUMIF` are all special cases of REDUCE with a particular accumulator type and reduction step. The win shows up the moment your aggregation is too custom for the built-ins: weighted averages, conditional sums with multiple branches, "second-highest value," "first match satisfying a complex condition."

<FunctionRef name="REDUCE" />

### Worked example 1: toy data

Sum a column the hard way. `REDUCE` with `0` as the initial accumulator and `acc + current` as the step is equivalent to `SUM`. The point is that you can see the mechanism.

## SCAN: REDUCE with every step preserved

`SCAN` has the same signature as `REDUCE` but returns the running accumulator at every step, not just the final value. The output is the same shape as the input array.

<FunctionRef name="SCAN" />

The canonical adtech use is the running cumulative spend. Sort the log by date, then `SCAN` produces a column showing how much was spent through each day. Plot it against the date column and you have the team's burn-rate chart.

```
=SCAN(0, E2:E13, LAMBDA(acc, spend, acc + spend))
```

On the campaign log this returns twelve values: `342.18, 540.58, 1153.48, ...`. Each row is the cumulative spend through that campaign. The first answers "did we hit $5,000 by mid-month?" without anyone writing a single helper column.

<TryIt

  task={<>Build a running cumulative Spend column. Put the SCAN formula in <code>H2</code> so it spills into <code>H2:H13</code>.</>}
  hint={<>Same signature as REDUCE but returns every step. <code>SCAN(initial, array, LAMBDA(acc, current, body))</code>.</>}
  answer={<>SCAN keeps every accumulator value, not just the last. Pair it with the campaign date column and you have a cumulative-spend chart with one formula. For a smoother weekly-running view, replace the LAMBDA body with a windowed accumulation, or sort the log by date first (lesson 1.14's SORT) so the cumulative reads in chronological order.</>}

## BYROW and BYCOL: collapse one dimension

`BYROW(range, LAMBDA(row, body))` applies the LAMBDA to each row of the range and returns a single column of results. `BYCOL(range, LAMBDA(col, body))` does the same for each column and returns a single row.

These are the right pick when the LAMBDA needs to see a whole row or column at once, typically because the body calls an aggregate like `SUM`, `AVERAGE`, `MAX` on it.

<FunctionRef name="BYROW" />

<FunctionRef name="BYCOL" />

```
=BYROW(E2:F13, LAMBDA(row, SUM(row)))   → per-row sum of Spend + Revenue
=BYCOL(E2:F13, LAMBDA(col, AVERAGE(col))) → average Spend, average Revenue (1×2 row)
```

In adtech, `BYROW` shows up most often for per-row profit margins over a multi-column range: `=BYROW(Campaigns[[Spend]:[Revenue]], LAMBDA(row, (INDEX(row,1,2)-INDEX(row,1,1))/INDEX(row,1,2)))`. `BYCOL` is the column-summary tool for wide pivot tables.

## MAKEARRAY: build an array from nothing

`MAKEARRAY(rows, cols, LAMBDA(row_index, col_index, body))` creates a fresh array. The LAMBDA receives the 1-indexed row and column and returns the cell value. Full canonical introduction is in lesson 1.11; here it slots into the helper family.

<FunctionRef name="MAKEARRAY" />

```
=MAKEARRAY(10, 10, LAMBDA(r, c, r * c))
```

A 10×10 multiplication table. In adtech work, `MAKEARRAY` is mostly used for scenario matrices (cost tier × ROI tier grids), calibration tables, and synthetic test data before a real `IMPORTRANGE` lands.

## When to choose which

| Need | Reach for |
|---|---|
| Apply a calc to every cell, same-shape output | `MAP` |
| Collapse an array into one value | `REDUCE` |
| Same as REDUCE, but keep every running step | `SCAN` |
| One value per row across a multi-column range | `BYROW` |
| One value per column across a multi-row range | `BYCOL` |
| Build a grid from row/column indices alone | `MAKEARRAY` |

For pure cell-wise math (markup, ROI per row, normalization), `MAP` and `ARRAYFORMULA` (lesson 1.10) do similar work. `ARRAYFORMULA` is older and sometimes a touch faster on very large arrays; `MAP` is more readable and explicit because the LAMBDA names its parameters. Default to `MAP`; reach for `ARRAYFORMULA` only when `MAP` is measurably slow.

## Used in the wild

- **`MAP` for the entire calculated-column shelf.** Bulk markups, normalizations, ROI per campaign, profit per row, cohort key derivation. Replaces drag-down formulas that grow stale on row addition.
- **`REDUCE` for the aggregations `SUMIFS` cannot do.** Weighted averages by spend share, conditional sums with three-way branches, "smallest non-zero value," "first row matching a complex predicate."
- **`SCAN` for running totals and burn-rate charts.** Cumulative spend, day-by-day budget burn, rolling revenue, drawdown curves.
- **`BYROW` for per-campaign aggregates across multiple columns.** Profit margin (Spend, Revenue), spread (Min, Max), composite score across a metric pivot.
- **`BYCOL` for summary rows across wide pivot tables.** Column averages on a per-buyer-per-vertical revenue grid, column variances for benchmark comparison.
- **`MAKEARRAY` for scenario matrices.** Sensitivity tables where each cell is computed from `(price_tier_index × roi_tier_index)`, synthetic test rows before the real `IMPORTRANGE` lands.

## Pro pitfalls

- **The LAMBDA's parameter count must match the call shape.** `MAP` with two arrays needs a two-parameter LAMBDA; `REDUCE` and `SCAN` always take two-parameter LAMBDAs (acc, current); `BYROW`/`BYCOL` take one-parameter LAMBDAs (the row or column). Mismatch returns a clear error message; pay attention to it.
- **`REDUCE`'s initial value sets the accumulator's type for the whole walk.** Use `0` for numeric, `""` for string concatenation, `{}` (an empty array) for array accumulation. Wrong type causes type errors deep inside the LAMBDA.
- **`BYROW` / `BYCOL` always return a column/row, even on single-row/column inputs.** A 1-row input to `BYROW` returns a 1-cell column, not a scalar. Wrap in `INDEX(..., 1, 1)` if you need a bare scalar.
- **`MAKEARRAY(rows, cols, ...)` cost is `rows × cols` LAMBDA calls.** `MAKEARRAY(1000, 1000, ...)` invokes the LAMBDA a million times. Sheets will slow to a crawl. Build only what you need.
- **No early termination.** `REDUCE` walks the entire array every time. There is no "stop when the condition is met." You can short-circuit the LAMBDA body (return `acc` unchanged on a flag), but you still pay for the full walk.
- **Volatile functions inside helpers recalculate on every change.** `LAMBDA(x, NOW() - x)` inside a `MAP` over a 1000-row range invokes `NOW()` a thousand times per recalc, and `NOW()` is volatile. The whole formula becomes volatile too. Avoid `NOW`/`TODAY`/`RAND`/`RANDARRAY`/`INDIRECT`/`OFFSET` inside helper LAMBDAs unless you really mean it.
- **Performance vs `ARRAYFORMULA`.** For cell-wise math, `MAP` and `ARRAYFORMULA` are roughly equivalent. `ARRAYFORMULA` can be faster on very large arrays; `MAP` is more explicit. Pick `MAP` for readability and switch only with measurements.
