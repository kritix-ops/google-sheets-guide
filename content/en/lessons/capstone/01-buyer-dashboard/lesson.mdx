# The buyer dashboard capstone: building a workbook end-to-end

Eighty lessons in, you have all the parts. Formulas that join, lookup, filter, and aggregate. A modeling vocabulary: pivots, conditional formatting, charts, scorecards. Apps Script for the work formulas cannot do on a schedule. Scale tooling for the day a sheet gets too big and pipes back from upstream sources. AI in the cells when the question is the kind only a model can answer. Until now, every lesson taught one part. This lesson is the part where you snap them together and build something that runs without you watching it.

The team's reality: Maya's group is launching the Q3 native-search blended portfolio. Five buyers, three platforms, twelve verticals. The Monday morning standup needs a dashboard that says, in one screen, what changed this week. Maya does not want to click anything to make that screen current. She wants to open the workbook at 09:00 and read it. Every part of the build below answers one piece of that requirement.

The shape is deliberate. Track 1 builds the math, Track 2 builds the visuals, Track 3 builds the schedule, Track 4 builds the pipes, Track 5 builds the prose. Drop any one of those and the dashboard is incomplete in a way that costs a different person a different hour. The diagnostic capstone in Track 4 lesson 11 is for when this kind of dashboard breaks. This lesson is for getting it right before it breaks.

## The scenario

Two upstream source workbooks contain the raw daily-level campaign data: `Taboola_Raw` and `Outbrain_Raw`. They live on someone else's account. The team's dashboard workbook pulls both via `IMPORTRANGE`, aggregates them into a per-buyer, per-vertical, per-day cube, and renders three views: scorecard tiles comparing this week to last week, a buyer-by-vertical pivot with conditional formatting, and a daily trend chart for spend versus revenue.

An Apps Script time-driven trigger runs every hour. It writes a refresh timestamp into the dashboard footer, alerts Maya by email if either `IMPORTRANGE` is returning `#REF!`, and appends a row to a `_AILog` tab so the audit trail keeps up with the refresh cycle. At the end of the week, a single `=AI()` call grounded on the aggregated table produces a one-paragraph "what changed" summary the trigger paste-as-values into a static cell at the bottom of the dashboard. By 08:55 Monday, when Maya opens the workbook, the numbers are current, the chart is current, the summary paragraph is current, and the audit trail has every step in it.

## Step 1: pull the raw data (IMPORTRANGE)

The first wire is the one you fix first when it breaks. Both IMPORTRANGE cells live on the Dashboard tab in column L. When you first paste an IMPORTRANGE formula referencing a workbook you have not pulled before, the cell shows `#REF!` with an "Allow access" pill. Click the pill, accept the prompt, and the cell resolves. Track 4 lesson 3 covers the full handshake; lesson 4.8 covers the failure modes you will hit later.

```
L1: =IMPORTRANGE("https://docs.google.com/spreadsheets/d/TABOOLA_RAW_ID/edit", "Taboola_Raw!A1:G500")
L2: =IMPORTRANGE("https://docs.google.com/spreadsheets/d/OUTBRAIN_RAW_ID/edit", "Outbrain_Raw!A1:G500")
```

Two things to notice. The range argument names the platform (`Taboola_Raw` vs `Outbrain_Raw`) so anyone reading the formula bar can tell which platform feeds which cell. The bound is `A1:G500` rather than full-column `A:G`; the team works with a few hundred rows of daily data, and a bounded pull is faster to refresh and cheaper on the upstream source. Bare `A:G` works for tiny feeds and starts to slow noticeably past a few thousand rows; lesson 4.1 covered why.

## Step 2: aggregate (QUERY + ARRAYFORMULA)

The aggregation is the heart of the dashboard. One `QUERY` formula at `J1` reads the per-row data and produces the per-buyer, per-vertical, per-day cube the rest of the dashboard reads from. Track 1 lessons 12 and 13 covered the SQL-like dialect; the key clauses for this build are `SELECT`, `GROUP BY`, and `LABEL`.

```
J1: =QUERY(A1:G62,
  "SELECT A, B, C, SUM(F), SUM(G)
   WHERE A IS NOT NULL
   GROUP BY A, B, C
   LABEL SUM(F) 'Spend', SUM(G) 'Revenue'", 1)
```

`SELECT A, B, C, SUM(F), SUM(G)` picks Date, Buyer, Vertical, summed Spend, and summed Revenue. `GROUP BY A, B, C` aggregates by the row dimensions. `LABEL` renames the summed columns so the headers read `Spend` and `Revenue` instead of the default `sum F`. The trailing `1` tells QUERY the source has one header row.

The reason the aggregation lives in one QUERY rather than a column of SUMIFS: one formula spills into a range, recalculates atomically, and reorganizes itself when new buyer-vertical pairs appear in the data. A wall of SUMIFS would require a static buyer-vertical grid you maintain by hand, and would silently miss a new vertical the first day it ships.

## Step 3: pivot and conditional formatting

The Buyer_Pivot tab gives Maya the cross-tab view: each buyer is a row, each vertical is a column, and the cells hold ROI. Insert → Pivot table → New sheet, name the sheet `Buyer_Pivot`, anchor at A1. Source range: `Dashboard!A1:G62`. Track 2 lesson 3 covers calculated fields in depth; the ROI field is the key one.

Pivot editor settings:

| Slot | Field | Notes |
|---|---|---|
| Rows | Buyer | One row per media buyer. |
| Columns | Vertical | One column per vertical (with the " PR" suffix from the team convention). |
| Values | Spend (SUM) | Track 2 lesson 2 covers the basic SUM aggregation. |
| Values | Revenue (SUM) | Same shape. |
| Values | Calculated field | Formula: `=('Revenue' - 'Spend') / 'Spend'`. Names the value `ROI`. |

The calculated field is the part that catches everyone the first time. ROI cannot be computed as an average of per-row ROIs; that would over-weight tiny campaigns. The calculated field uses the summed totals as inputs, so the buyer-vertical ROI cell shows `(SUM(Revenue) - SUM(Spend)) / SUM(Spend)` — the right ROI for the group.

The color scale is what makes the pivot useful at a glance. Format → Conditional formatting → Color scale on the ROI column. Set the mid-point as a number, value `1.0` (break-even). Below the mid-point is unprofitable, above is profitable. Track 2 lesson 6 covered the rule shape; this is the same rule applied to the most consequential column in the workbook.

## Step 4: scorecard tiles and trend chart

Three cells in column N hold the week-over-week scorecard. Track 2 lessons 9 through 11 covered the chart-and-tile pattern; the scorecard tiles are the textual sibling of the same idea.

```
N1: =SUMIFS(F2:F62, A2:A62, ">="&TODAY()-7)
N2: =SUMIFS(G2:G62, A2:A62, ">="&TODAY()-7)
N3: =N2/N1 - 1
```

`SUMIFS` filters by date range; the criterion `">="&TODAY()-7` includes everything in the last 7 days. Live dashboards do use `TODAY()`, despite the volatility warning from Track 1 lesson 8 — the scorecard is the one place where the cost is worth it because the answer literally has to be "this week." If the workbook gets slow as data piles up, the fix is to bound the range tighter (`F2:F62` here instead of `F:F`), not to drop the date filter.

For the daily trend chart: select `A2:A62` and `F2:F62` and `G2:G62`, Insert → Chart, type Line. Two series (Spend, Revenue), one x-axis (Date). Track 2 lesson 10 covered axis customization; for a dashboard, set the chart title to "This week vs last week" and pin the chart to a fixed position next to the scorecard tiles so the eye can compare numbers and trend in one glance.

## Step 5: auto-refresh (Apps Script)

The hourly refresh is the part of the dashboard that runs without Maya watching. Open Extensions → Apps Script from the workbook to bring up the bound script editor. Track 3 lesson 7 covered simple triggers; lesson 3.8 covered installable ones. A time-driven trigger is an installable trigger; the simple `onEdit` and `onOpen` triggers cannot do it.

You will write two functions. `setupHourlyRefresh()` is the registration step you run once from the editor; it accepts the auth prompt and registers the trigger. `refreshDashboard()` is the handler the trigger fires every hour.

```js
function setupHourlyRefresh() {
  ScriptApp.newTrigger("refreshDashboard")
    .timeBased()
    .everyHours(1)
    .create();
}

function refreshDashboard() {
  var ss = SpreadsheetApp.getActiveSpreadsheet();
  var dash = ss.getSheetByName("Dashboard");
  // Read the IMPORTRANGE cells; alert Maya if either is broken.
  var l1 = dash.getRange("L1").getValue();
  var l2 = dash.getRange("L2").getValue();
  if (String(l1).indexOf("#REF") !== -1 || String(l2).indexOf("#REF") !== -1) {
    MailApp.sendEmail(
      "maya@team.example",
      "Dashboard IMPORTRANGE broken",
      "L1 or L2 returned #REF! at " + new Date()
    );
  }
  // Write the refresh timestamp to the footer.
  dash.getRange("P5").setValue("Last refresh: " + new Date());
  // Append a row to _AILog so the audit trail keeps up.
  ss.getSheetByName("_AILog").appendRow([
    new Date(),
    "weekly summary",
    "gemini-2.5-flash",
    dash.getRange("P1").getValue()
  ]);
}
```

`setupHourlyRefresh` runs once from the editor's Run button. From then on, the trigger fires hourly without anyone touching it. The handler does three things: alerts on broken upstream, writes the timestamp footer, and logs the AI summary that's currently in P1 to the audit tab.

## Step 6: the weekly AI summary (=AI() with audit trail)

The summary cell is the only AI in the build. One call, grounded on the aggregated week, producing one paragraph. Track 5 lesson 2 covered prompt engineering; the patterns from lesson 5.6 (audit-trail-sensitive contexts) explain why the trigger paste-as-values it into a static form.

```
P1: =AI(
  "Summarize the week's spend and revenue trend for an exec audience.
   Name the strongest buyer-vertical combination by ROI.
   One short paragraph, no bullet points.",
  A1:G62
)
```

The second argument is the grounding range. Without it, Gemini speculates against whatever the active tab snapshot looks like, and the result drifts between calls. Lesson 5.1 covered why that drift is the most common AI-in-Sheets failure mode.

The audit trail is where the build earns its production grade. The trigger reads P1 each hour and appends the model's response to `_AILog` with a timestamp, the prompt name, and the model version. Lesson 5.6 explained the pattern: AI in cells is convenient, AI in cells with no audit trail is irresponsible. The `_AILog` tab is the difference.

```
_AILog tab columns:
A: Timestamp        B: Prompt name      C: Model version    D: Response
```

For the Monday email itself, the team paste-as-values the P1 cell into a static "Monday brief" tab once a week. From that point on, the paragraph cannot drift; the live `=AI()` keeps regenerating in P1 each hour, and the frozen Monday brief sits in its own tab as the historical record.

## The assignment

The assignment is the build. You start with the Dashboard tab seeded with the per-row campaign data and column-I labels for the eight target cells. The grader runs eleven rules across the seven file structures: L1, L2, J1, N1, N2, N3, P1, the Buyer_Pivot tab and its calculated field, the color-scale conditional format on Buyer_Pivot, the `_AILog` tab with a header row plus at least one seeded entry, and the Apps Script `refreshDashboard` handler with a productive body that touches `_AILog`.

One rule the grader cannot directly verify: that you registered the time-driven trigger by running `setupHourlyRefresh()` from the Apps Script editor. The grader reads the script source and confirms the function exists, but the trigger registration itself lives in a per-user table the grader cannot see. Run `setupHourlyRefresh()` once from the editor, accept the auth prompt, and confirm in the Triggers screen that a 1-hour time-based trigger appears. The lesson assumes you did that step.

## Pro pitfalls

- **Building outputs before inputs.** Writing the scorecard SUMIFS before the IMPORTRANGE cells are wired up means the tile shows zero until you wire the upstream. The zero looks fine; it is wrong. Build inputs first, outputs second.
- **Pivoting ROI by averaging.** A pivot that takes the AVERAGE of per-row ROIs is the most common adtech dashboard bug. The calculated field is the only correct pattern; everything else over-weights tiny campaigns.
- **Forgetting to paste-as-values the AI summary into the Monday brief.** A live `=AI()` cell in a deck you sent to the exec team is a paragraph that can rewrite itself. Paste-as-values into a static tab as soon as the standup deck ships.
- **No alert on broken IMPORTRANGE.** A dashboard that silently shows stale numbers when an upstream breaks is worse than a dashboard that shows `#REF!`. At least `#REF!` tells you to look. Silent staleness gets sent to execs.
- **No `_AILog` until the first incident.** The audit trail starts on day one. After-the-fact reconstruction is impossible; the trigger has to log from the first run.
- **Hourly trigger with a slow handler.** If `refreshDashboard` takes 5 minutes to run, you have not built an hourly refresh, you have built a 5-minute-out-of-every-hour outage. Track 3 lesson 16 covers batching; the handler above is small enough to finish in seconds, but check the Executions dashboard the first week.
