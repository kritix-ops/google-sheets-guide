# Sidebars ו-modal dialogs (HtmlService)

Custom functions חיות בתאים. Triggers יורים על events. **Sidebars** ו-**modal dialogs** הם משטח ה-UI השלישי, פאנלים מלאים של HTML מעוגנים ל-spreadsheet, שמתארחים על ידי Apps Script דרך ה-API של `HtmlService`. הם מאפשרים לבנות forms, אשפי רב-שלביים, dashboards, וזרימות אישור שחיות לצד הרשת ולא בתוכה.

שלוש צורות שאותו פלט HtmlService יכול לקבל:

| מתודה | מה היא מייצרת |
|---|---|
| `showSidebar(html)` | פאנל קבוע ברוחב 300px מעוגן מימין לרשת. המשתמש יכול להמשיך לערוך את ה-sheet בזמן שה-sidebar פתוח. |
| `showModalDialog(html, title)` | חלון צף ממורכז. חוסם את שאר ה-sheet עד שמסולק. שימושי ל-confirms ול-inputs של צעד אחד. |
| `showModelessDialog(html, title)` | חלון צף ממורכז שלא חוסם את ה-sheet. פחות נפוץ; שימושי ל-inspectors שמתעדכנים כשהמשתמש זז. |

כל השלוש נקראים על `SpreadsheetApp.getUi()`. כל השלוש לוקחים `HtmlOutput` שנבנה על ידי `HtmlService`.

## בניית HtmlOutput

שתי דרכים לבנות את ה-output:

```js
// מתוך קובץ בפרויקט Apps Script. הנפוץ ביותר, שומר HTML
// בנפרד מ-JS, מקבל הדגשת תחביר בעורך.
const html = HtmlService.createHtmlOutputFromFile("Reports");

// מתוך מחרוזת inline. שימושי ל-prompt חד-פעמי מהיר; לא סקיילבילי.
const html = HtmlService.createHtmlOutput("<h2>Report</h2><p>...</p>");
```

הארגומנט ל-`createHtmlOutputFromFile` הוא **שם הקובץ כמו שמופיע בעורך Apps Script**, לא שם הקובץ בדיסק. העורך שומר קבצי HTML עם סיומת `.html` אוטומטית; מתייחסים אליהם בלי הסיומת. `"Reports"` בקוד, `Reports.html` בבורר הקבצים.

ואז משרשרים על ה-output כדי להגדיר title ומידות:

```js
const html = HtmlService.createHtmlOutputFromFile("Reports")
  .setTitle("Reports")
  .setWidth(300)  // רק dialogs, sidebars מתעלמים מזה ותמיד ברוחב 300px
  .setHeight(400); // רק dialogs
```

`setTitle` היא הכותרת הגלויה בראש ה-sidebar או ה-dialog. דילוג עליה והפאנל עדיין עובד, אבל ה-header נשאר ריק.

## הערה על ה-sidebar של הקורס

הפרויקט המקושר של הקורס כבר כולל קובץ HTML שמור בשם `Sidebar`, זה ה-shell שמארח את ה-companion בתוך ה-spreadsheet שאתם קוראים כרגע. אי אפשר להשתמש ב-`"Sidebar"` כשם קובץ לעבודה שלכם בשיעור הזה: ה-provisioner ישמיט בשקט כל קובץ seed עם השם הזה, ו-`createHtmlOutputFromFile("Sidebar")` יצביע על shell הקורס, לא על הקוד שלכם. המטלה משתמשת ב-**`"Reports"`** במקום. מחוץ לקורס, ב-spreadsheet משלכם, אפשר לקרוא לקובץ ה-HTML איך שרוצים.

## ה-sandbox

ה-HTML שאתם טוענים רץ בתוך **iframe** שמוגש מ-`googleusercontent.com`, לא מהדומיין של ה-spreadsheet. יש לזה כמה השלכות שכדאי לדעת לפני שכותבים sidebar מורכב:

- **`<base target="_top">` שייך לכל `<head>`.** בלעדיו, לינקים בתוך ה-sidebar נפתחים בתוך ה-iframe (ונשברים, כי ה-iframe ב-sandbox). איתו, הם נפתחים ב-tab ההורה. כל template של HtmlService ש-Google שולחת מתחיל ב-tag הזה.
- **אין גישה ישירה ל-spreadsheet מתוך ה-HTML.** ה-HTML לא יכול לקרוא או לכתוב תאים, לא יכול לקרוא ל-`SpreadsheetApp`. כדי לעשות את הדברים האלה, ה-JS בצד ה-client קורא חזרה ל-Apps Script בצד ה-server דרך `google.script.run`. (אנחנו נוגעים בזה למטה; track מאוחר יותר מכסה את זה לעומק.)
- **`position: fixed` ו-`position: sticky` לא עובדים** כמו שמצפים בתוך ה-sandbox. הם מתנהגים כמו static positioning. אם רוצים sticky footer, משתמשים ב-`position: absolute` בתוך container עם relative positioning שממלא את גובה ה-iframe.
- **משאבים חיצוניים כפופים ל-Content Security Policy של ה-iframe.** אפשר לקשר ל-CDN של stylesheet או font מ-host שמותר ב-CSP (Google Fonts עובד; CDNs שרירותיים אולי לא). `<style>` inline ו-`<script>` inline עובדים מצוין.
- **URLs יחסיים לשרת שלכם לא מתפענחים.** ה-origin של ה-iframe הוא של Google, לא שלכם. תמונות, fonts, ו-scripts שאתם "מארחים" עובדים רק אם הם מוגשים מ-URL מוחלט של https.

## קריאות client-to-server (תצוגה מקדימה)

קובץ ה-HTML יכול לכלול בלוקים של `<script>`. כדי לקרוא חזרה לקוד `.gs`, משתמשים ב-`google.script.run`:

```html
<script>
  function refresh() {
    google.script.run
      .withSuccessHandler(function(spend) {
        document.getElementById("spend").innerText = spend;
      })
      .getTodaysSpend();
  }
  refresh();
</script>
```

`getTodaysSpend` היא function שמוכרזת ברמה העליונה של איזשהו קובץ `.gs` בפרויקט. Apps Script מגשר את הקריאה מעבר לגבול ה-sandbox. אנחנו מזכירים את זה כאן כי רוב ה-sidebars הלא טריוויאליים זקוקים לזה; track מאוחר יותר מכסה את ה-lifecycle המלא של client-server.

## מתי לבחור איזו צורה

- **Sidebar**: זרימות רב-שלביות, UI קבוע שהמשתמש רוצה לשמור פתוח בזמן עבודה ברשת. ה-"Campaign builder" של הצוות הוא sidebar: שדות form מובילים את ה-buyer דרך מתן שם לקמפיין חדש, בחירת vertical מהרשימה הקנונית, בחירת פלטפורמה, יצירת המחרוזת של שם הקמפיין. הוא נשאר פתוח לאורך עריכות ה-sheet.
- **Modal dialog**: confirms חד-שלביים ו-inputs של צעד אחד. "להעביר 47 קמפיינים מושהים לארכיון? [Cancel] [Archive]." טבע החסימה הוא הפיצ'ר: הוא מונע מהמשתמש ללחוץ במקום אחר באמצע ה-confirm.
- **Modeless dialog**: נדיר. פאנלים של inspector שמתעדכנים על בחירה הם השימוש העיקרי. בפועל, sidebars מטפלים ברוב אותן עבודות באלגנטיות גדולה יותר.

## נפוץ בשטח

שני דפוסים מהצוות:

- **Sidebar של Campaign builder.** form רב-שלבי: בוחרים את ה-buyer, בוחרים את ה-vertical מרשימת PR הקנונית, בוחרים את הפלטפורמה, בוחרים את המדינה, בוחרים את סוג הקמפיין (`permax`, `rsoc`, `s1d`, `tc`). בלחיצת submit, ה-sidebar קורא לפונקציה בצד ה-server שבונה את המחרוזת של שם הקמפיין מהחלקים ומוסיפה שורה חדשה ל-log הקמפיינים. ה-form המלא חי ב-`Sidebar.html` (ב-spreadsheet שלהם, לא בקורס הזה, הם לא משתפים את השם השמור) וה-row-append בצד ה-server ב-`Code.gs`.
- **Dialog של אישור bulk-archive.** כשה-buyer בוחר 50+ שורות ולוחץ "Archive selected", modal dialog נפתח עם מספר השורות, טווח התאריכים, וה-spend הכולל שמכוסה. שני כפתורים: Cancel ו-Archive. התנהגות החסימה קריטית פה, בחירת השורות שורדת את ה-modal, אז המשתמש לא יכול לאבד את ה-context תוך כדי אישור.

## מלכודות מקצועיות

- **ה-tab של ה-sidebar לא שורד reload.** מרעננים את ה-spreadsheet וה-sidebar נסגר בשקט. אם יש "Show sidebar" בתפריט מותאם, המשתמש פשוט לוחץ עליו שוב. לא שומרים state קריטי ב-sidebar, מחזיקים אותו בתאים או ב-`PropertiesService` של ה-script כדי ש-reload לא יאבד אותו.
- **Modal dialogs חוסמים את כל ה-sheet.** בלי עריכה, בלי גלילה, בלי לחיצות במקום אחר עד שהמשתמש מסלק את ה-dialog. משתמשים בהם במשורה, הם שוברים זרימה אם משתמשים בהם לכל דבר חוץ מ-confirm חד-שלבי.
- **`setTitle` על sidebar הוא הכותרת הגלויה בראש הפאנל.** אם מגדירים אותו למחרוזת ריקה, ה-header ריק אבל לפאנל עדיין יש top bar.
- **שם קובץ ה-HTML רגיש לאותיות גדולות וקטנות.** `createHtmlOutputFromFile("reports")` לא מוצא את `Reports.html`. בורר הקבצים של העורך מראה את ה-capitalization הקנונית.
- **paths יחסיים לא עובדים לתמונות ול-fonts.** ה-iframe מוגש מ-`googleusercontent.com`, לא מהדומיין של ה-spreadsheet. משתמשים ב-URLs מוחלטים של https ל-host שאתם שולטים בו.
- **`position: fixed` נזרק בשקט בתוך ה-iframe.** Footers ו-toolbars sticky צריכים markup אחר, בדרך כלל flex container עם `flex-direction: column` ו-footer שלוקח את הגובה הטבעי שלו בתחתית.
- **scripts חיצוניים נתקלים בקיר CSP.** `<script src="https://some-cdn/jquery.js">` אולי ייטען (Google Fonts מותר; חלק מה-CDNs לא), זה תלוי ב-allowlist של Google שמשתנה. הדפוס העמיד: inline את ה-JS שאתם צריכים, או vendor אותו לבלוק ה-`<script>` של קובץ ה-HTML.
- **HTML של sidebar אין לו גישה לתאים.** אי אפשר לכתוב `document.getElementById("a1").innerText = spreadsheet.getRange("A1").getValue()`. קריאות וכתיבות עוברות דרך `google.script.run` מה-client חזרה ל-function `.gs`. ה-sandbox הוא הקיר.
- **שם הקובץ השמור `"Sidebar"` בקורס הזה.** אם שמים `"Sidebar"` ב-`createHtmlOutputFromFile(...)`, אתם תקבלו או את shell הקורס (לא את הקוד שלכם) או שגיאת "file not found" אם ה-shell לא מקושר. המטלה משתמשת ב-`"Reports"` כדי להימנע מההתנגשות.
