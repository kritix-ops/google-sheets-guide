# קריאה ל-APIs חיצוניים מ-Apps Script: UrlFetchApp, OAuth, וקריאה ל-Slack / Linear / GitHub

עד עכשיו Track 3 נשאר בתוך המשטח של Google: תאים, ה-sheet, Drive, Gmail, Calendar. scripts אמיתיים בעולם האדטק מבלים את רוב הזמן בשיחה עם שירותים *אחרים*. ה-API של Taboola backstage לנתוני spend גולמיים. Slack להתראות ROI. Linear ליצירת tickets כש-media buyer מסמן קמפיין. GitHub כש-Cloud Function deployed צריך redeploy. כל אחת מהקפיצות האלה עוברת דרך API אחד של Apps Script: **`UrlFetchApp`**.

השיעור הזה עוסק ב-options bag שלו, ב-patterns לשיחה עם API של JSON, בצורות auth שבאמת עובדות בפועל, ובמשמעת טיפול שגיאות ששומרת cron לילי בחיים אחרי שלשותף יש אחר צהריים רע. אם תתפסו את השיעור נכון, תוכלו לחבר את Apps Script כמעט לכל דבר בצורת HTTP בלי לעזוב את ה-bound script.

## הצורה של קריאת fetch

```js
const response = UrlFetchApp.fetch("https://example.com/api/taboola/summary", {
  method: "get",                       // ברירת מחדל; כלול לבהירות
  headers: { Authorization: "Bearer demo-token" },
  muteHttpExceptions: true,            // קריטי, ראו למטה
});

const code = response.getResponseCode();
const body = response.getContentText();
const data = JSON.parse(body);
```

הארגומנט הראשון הוא ה-URL. השני הוא **options bag** שמניע כמעט כל דבר מעניין על הקריאה:

| אפשרות | מה זה עושה |
|---|---|
| `method` | `"get"` (ברירת מחדל), `"post"`, `"put"`, `"patch"`, או `"delete"`. case-insensitive. |
| `headers` | object רגיל של header-name לערך. `Authorization`, `Accept`, headers מותאמים של פלטפורמה חיים כאן. |
| `payload` | ה-body של ה-request. מחרוזת נשלחת כפי שהיא; object הוא form-urlencoded (לא JSON-encoded: ראו שורה הבאה). |
| `contentType` | אם מגדירים את זה ומעבירים `payload` מחרוזת, Apps Script שולח בדיוק מה שכתבתם. כדי לעשות POST של JSON מגדירים `contentType: "application/json"` ומעשים stringify ל-payload בעצמכם. |
| `muteHttpExceptions` | כש-`true`, 4xx או 5xx מחזיר response object שאפשר לבדוק. כש-`false` (ברירת מחדל), Apps Script זורק ולא ניתן לקרוא את ה-body של השגיאה. **כמעט תמיד מגדירים את זה ל-`true`.** |
| `followRedirects` | ברירת מחדל `true`. מגדירים `false` ל-endpoints של tracking-pixel שבהם ה-302 הוא התשובה. |

## OAuth וטיפול ב-tokens

שלושה patterns מכסים כמעט הכל שתעשו:

1. **token סטטי ב-`PropertiesService`.** ה-URL של ה-webhook של Slack של הצוות וה-token של ה-API של Linear חיים ב-user properties של ה-script, מוגדרים פעם אחת דרך `PropertiesService.getScriptProperties().setProperty("LINEAR_TOKEN", "lin_api_...")`. ה-script קורא עם `getProperty` בזמן הקריאה. ה-token אף פעם לא נוחת במקור, מה שאומר שהוא לא נכנס ל-git כשמישהו עושה export ל-Apps Script project.

2. **ספרייה OAuth2 לזרימות מלאות.** כשצריך ריקוד OAuth (Google, GitHub, כל דבר עם refresh token), הספרייה המתוחזקת על ידי הקהילה **OAuth2 for Apps Script** מטפלת ב-redirect URI, ב-token exchange, וב-refresh עם פקיעה. מוסיפים אותה כ-dependency של ספרייה (שיעור 12 מכסה איך) וקוראים ל-`OAuth2.createService(...)` פעם אחת לכל שירות.

3. **URLs של webhook שהם עצמם הסוד.** webhooks נכנסים של Slack הם הנקיים ביותר. ה-URL מכיל את ה-auth, אתם עושים POST ל-body של JSON, ואין token לנהל. מתייחסים ל-URL כסוד (זה עדיין הולך ל-`PropertiesService`, לא למקור).

## מגבלות קצב ומכסות

המכסה של Apps Script עצמו על `UrlFetchApp` היא **20,000 קריאות ביום** לחשבונות consumer, **100,000 / יום** ל-Workspace. רוב ה-scripts פוגעים במגבלת הקצב של השירות היעד הרבה לפני שהם פוגעים בזו של Apps Script. gotchas נפוצים:

- **Slack incoming webhooks**: 1 הודעה לשנייה לכל URL webhook. לולאה של מאה ב-burst הדוק ו-90 האחרונות נופלות בשקט בצד של Slack.
- **Linear API**: 1,200 בקשות לשעה לכל access token. script שיוצר tickets בהמוניים צריך exponential backoff בתוך הלולאה.
- **GitHub API (לא מאומת)**: 60 לשעה לכל IP מקור. מאומת (עם personal access token) קופץ ל-5,000 לשעה.
- **Taboola, Outbrain, MediaGo**: מתועדים ב-"היו הגיוניים", מה שבפועל אומר כמה מאות בקשות לשעה לפני שהם 429 אתכם. תמיד בודקים את ה-docs לפני קנה מידה.

`UrlFetchApp.fetchAll(requests)` עושה parallelize ל-batch של fetches עם קריאת method אחת, שזה גם חוסך מכסה (זה נספר כ-round-trip אחד מצד Apps Script, אם כי כל fetch בודד עדיין נספר כקריאה אחת מול היעד שלכם) וזה דרמטית מהיר יותר מ-loop טורי. ה-catch: זה מחזיר כשכל הבקשות הסתיימו, אז בקשה אחת איטית חוסמת את כל ה-batch.

## Webhooks מול polling

שתי דרכים לאינטגרציה עם שירות חיצוני:

- **Webhook** = הם קוראים אליכם. השירות עושה POST ל-URL שאתם חושפים (ראו שיעור 13 איך לפרוס doPost endpoint). אתם מגיבים. fire-and-forget בצד שלהם; אין לכם שליטה מתי זה יורה.
- **Polling** = אתם קוראים אליהם. trigger מבוסס-זמן כל N דקות, אתם עושים `UrlFetchApp.fetch` לנתונים חדשים, אתם כותבים את ה-diff ל-sheet.

התראות Slack קלות כי Slack מציעה *מקבלי* webhook (incoming webhooks): אתם עושים POST ל-URL שלהם כשמשהו מעניין קורה ב-script שלכם, אין צורך ב-polling. GitHub ו-Linear הולכים בשני הכיוונים: הם מציעים webhooks ל-events שהם פולטים, ו-APIs לפעולות שאתם לוקחים.

## טיפול שגיאות

הצורה הכנה וההגנתית:

```js
function fetchWithRetry(url, options, maxAttempts = 3) {
  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    try {
      const response = UrlFetchApp.fetch(url, {
        ...options,
        muteHttpExceptions: true,
      });
      const code = response.getResponseCode();
      if (code >= 200 && code < 300) return response;
      if (code >= 500 && attempt < maxAttempts) {
        // שגיאת שרת: מחכים ומנסים שוב עם backoff.
        Utilities.sleep(1000 * Math.pow(2, attempt - 1));
        continue;
      }
      // שגיאות 4xx לא חוזרות; צורת הבקשה שגויה.
      throw new Error(`HTTP ${code}: ${response.getContentText()}`);
    } catch (err) {
      if (attempt === maxAttempts) throw err;
      // שגיאות רשת (DNS, connection reset) מקבלות retry גם.
      Utilities.sleep(1000 * Math.pow(2, attempt - 1));
    }
  }
}
```

זה מוגזם להודעת Slack של one-shot. לכל דבר שרץ על time-driven trigger ושהצוות תלוי בו, זה המינימום הבסיסי.

## נפוץ בשטח

האינטגרציות החיצוניות של הצוות הן כולן וריאציות של השיעור הזה:

- **התראות Slack על ירידות ROI.** trigger מבוסס-זמן קורא את ה-tab של Aggregator, מקבץ לפי buyer, ולכל buyer ש-ROI של 7 ימים שלו ירד מתחת ל-1.0 הוא עושה POST ל-incoming webhook של Slack עם JSON payload כמו `{ "text": "buyer Yoav: 7d ROI dropped to 0.82" }`. URL webhook אחד מאוחסן ב-`PropertiesService`.
- **יצירת ticket ב-Linear מכפתור sidebar.** כפתור ה-sidebar "Flag this campaign" אוסף את שם הקמפיין של השורה ואת הסיבה, עושה POST ל-`https://api.linear.app/graphql` עם ה-mutation `issueCreate` של GraphQL, וכותב את ה-URL של ה-ticket שנוצר לעמודת sheet. ה-token של Linear API מגיע מ-`PropertiesService`.
- **תגובת GitHub על עדכוני אגרגטור.** כשהאגרגטור הלילי מסיים, function follow-up מפרסמת תגובה ל-issue ב-GitHub שעוקב אחרי הריצה היומית, עם טבלת סיכום Markdown. personal access token ב-`PropertiesService`.

כל אחד מהם הוא אותה צורה של חמש שורות: לקבל את הסוד, לבנות את ה-body, fetch, לבדוק את קוד התגובה, לכתוב log או לכתוב את התוצאה.

## מלכודות מקצועיות

- **`muteHttpExceptions: false` (ברירת המחדל) זורק על 4xx ו-5xx כך שלא ניתן לראות את ה-body של השגיאה.** תמיד מגדירים את זה ל-`true`. המקרים הבודדים שבהם רוצים את ההתנהגות ברירת מחדל: הקוד שלכם עוטף את ה-fetch ב-try/catch שזורק שוב: תדעו את זה.
- **Apps Script שומר ב-cache fetches עם אותו URL + headers בחלון קצר.** loop של retry צמוד שפוגע באותו URL מקבל responses ב-cache. כדי לכפות בקשה טרייה, מצמידים פרמטר cache-busting: `url + "?ts=" + Date.now()`.
- **OAuth tokens שהולכים מיושנים.** token ב-`PropertiesService` שעבד חודש שעבר לא תמיד עובד היום. tokens של Linear ו-GitHub יכולים להיות מבוטלים או לפוג כשהמשתמש שהנפיק עוזב את ה-org. בונים את ה-script לרשום log של קוד התגובה, ועושים את האגרגטור היומי שולח מייל למישהו כשהוא רואה 401: כשלים שקטים הם הגרועים ביותר.
- **`UrlFetchApp.fetchAll` חוסם על הבקשה האיטית ביותר ב-batch.** אם אתם משגרים 50 fetches בארבעה שירותים שונים ואחד מהם עובר דקה רעה, כל ה-batch מחכה. מפצלים את ה-batch לפי שירות אם אחד מהם לא אמין.
- **`payload` form-urlencoded כשהתכוונתם ל-JSON.** הגדרת `payload: { foo: "bar" }` ללא `contentType` שולחת `foo=bar`, לא `{"foo":"bar"}`. ה-API מגיב עם "invalid JSON" ואתם מבלים שעה בקריאת ה-docs הלא נכונים. ברירת מחדל ל-`contentType: "application/json"` פלוס `payload: JSON.stringify(...)` לכל JSON API שאינו של Google.
- **URLs של Webhook שמופקדים בטעות במקור.** URL webhook של Slack הוא ה-auth: כל מי שיש לו את ה-URL יכול לפרסם לערוץ שלכם. תמיד קוראים אותו מ-`PropertiesService.getScriptProperties()` (שיעור 15 מכסה Properties + Cache מקצה לקצה), אף פעם לא inline אמיתי בקוד. אם אתם מגלים אחד במקור, מבצעים rotation מ-admin של Slack לפני שעושים שום דבר אחר.
- **מגבלת body של response של 50 MB.** response גדול של GitHub API (רשימה של issues עם bodies מלאים) יכול לחרוג מזה. משתמשים ב-pagination של ה-API (ה-`Link` header) וב-`UrlFetchApp.fetchAll` לדפים במקביל.
- **מצב HTTPS קפדני.** Apps Script מאמת את התעודה. endpoints של בדיקה עם תעודה עצמית נכשלים. אין דגל לדלג על אימות; פורסים תעודה אמיתית על היעד (Let's Encrypt בחינם) והבעיה נעלמת.
