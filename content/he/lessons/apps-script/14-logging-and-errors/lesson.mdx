# Logging, טיפול בשגיאות, וסיפור Cloud Logging

שלושה-עשר השיעורים הראשונים ב-Track 3 כיסו קוד שעושה עבודה: custom functions, תפריטים, macros, triggers, ה-surface של `SpreadsheetApp`. השיעור הזה מכסה את החלק שאף אחד לא חושב עליו עד שמשהו נשבר בשתיים בלילה: איך רואים מה הקוד עשה, ואיך שורדים כשמשהו משתבש. ה-Taboola pull הלילי של הצוות, ה-trigger שמרענן את ה-dashboard לכל media buyer, ה-trigger שמטפל ב-fallback של IMPORTRANGE, לכל אחד מהם צריך logs כדי לענות "האם זה רץ?" וטיפול בשגיאות כדי ששורה גרועה אחת לא תפיל את כל ה-batch.

השיעור הזה מכסה ארבעה דברים: שני משטחי ה-logging (`console.log` ו-`Logger.log`) ובאיזה להשתמש; רמות חומרה ו-logging מובנה שמתרחבים לאלפי entries; צורת ה-try/catch שכל handler ב-production משתמש בה; ומודל השמירה של Cloud Logging פלוס איך הצוות עוקף אותו. תתפסו את השיעור הזה נכון והחקירה הבאה של "משהו נשבר ביום שישי שעבר" מסיימת תוך דקות במקום שעות.

## שני משטחי logging, בחירה אחת שפויה

ל-Apps Script יש שתי דרכים להדפיס:

```js
console.log("Read spend: " + spend);   // מודרני. משתמשים בזה.
Logger.log("Read spend: " + spend);    // מורשת. עדיין עובד.
```

שני השורות מופיעות באותו מקום. פותחים את עורך Apps Script, לוחצים על אייקון ה-**Executions** ברצועת השמאל (השעון עם החץ), וכל ריצה אחרונה מופיעה עם ה-logs מצורפים. `console.log` הוא ה-surface שלאחר 2020; `Logger.log` הוא הישן יותר שקדם לאינטגרציה עם Cloud Logging של Google.

שני ההבדלים ששווה לדעת:

| | `console.log` | `Logger.log` |
|---|---|---|
| רמות חומרה | `info`, `warn`, `error`, `debug` דרך `console.log/warn/error/debug` | רמה אחת (info). |
| צורת הארגומנט | מקבל מספר args ו-object literals, מפורמט כ-JSON. | מחרוזת יחידה. multi-arg משורשר עם פסיקים. |
| סינון Cloud Logging | חומרות מסננות native (`severity=ERROR`). | כל ה-entries נוחתים ברמת info. |
| המלצה | מעדיפים את זה לכל דבר חדש. | משאירים קוד קיים לבד; לא מוסיפים קריאות חדשות. |

ברירת מחדל ל-`console.log`. הזמן היחיד ש-`Logger.log` עדיין מנצח הוא כשאתם טלאים על קוד מורשת ורוצים להתאים לסגנון מסביב.

## חומרה חשובה כשיש לכם מאות ריצות

ה-trigger הלילי של הצוות רושם ~200 שורות לריצה. על פני חודש זה ~6,000 entries. ה-Executions panel וה-Cloud Logging viewer שניהם מאפשרים סינון לפי חומרה, וה-filter הזה הוא הדרך היחידה למצוא מה באמת השתבש:

```js
console.log("Trigger fired at " + new Date());     // info, טובע ברעש
console.warn("Vertical name missing PR suffix");    // warn, שווה מבט
console.error("Failed to write row " + row + ": " + e.toString()); // error, מתקשרים למישהו
```

ב-Cloud Logging, מחליפים את ה-filter של החומרה ל-**Error and above** ונשארים עם 5 ה-entries שבאמת צריכים תשומת לב. כשהכל ברמת info (העולם של `Logger.log`) אתם גוללים דרך 6,000 שורות לציד את הרעה.

## try/catch היא צורת ה-handler של production

כל handler של trigger ב-workbooks של הצוות נראה ככה:

```js
function nightlyPull() {
  try {
    const data = fetchTaboolaData();
    writeToCampaignsSheet(data);
    console.log("Nightly pull complete: " + data.length + " rows");
  } catch (e) {
    console.error("Nightly pull failed: " + e.toString());
    console.error(e.stack);
    // מעלים לצוות. בלי זה, ה-trigger ינסה שוב בשקט מחר
    // ולא תשימו לב במשך שבוע.
    MailApp.sendEmail("team@flexelent.com", "Nightly pull broke", e.toString());
  }
}
```

שלושה חלקים, כולם שווים לעשות:

1. **`try`** עוטף את העבודה שיכולה לזרוק. הקורא, הכותב, כל `UrlFetchApp.fetch` ל-endpoint צד-שלישי.
2. **`catch (e)`** מקבל את ה-exception. `e.toString()` היא ההודעה הקצרה; `e.stack` הוא stack trace.
3. **תופעת לוואי על כשל**, בדרך כלל מייל או Slack webhook או כתיבה לגיליון error log. ה-catch block רץ ב-auth context של ה-trigger, אז הוא יכול לשלוח מייל. ה-handler שלא מודיע הוא ה-handler שאף אחד לא יודע שהוא שבור.

אם הקורא אכפת לו מהכשל (שרשרת של triggers שבה הבא לא צריך לרוץ), `throw e` בסוף ה-catch אחרי תופעת הלוואי. ה-exception מתפשט למעלה. אם הקורא הוא ה-runtime עצמו (ה-trigger שירה את זה), בליעת ה-exception נכונה, כבר רשמתם log.

## Logs מובנים מנצחים שרשור מחרוזות

שורת log שאומרת `"Failed to write row 17: TypeError: cannot read property 'length' of undefined"` בסדר לקריאה. היא נוראית לסינון. ה-triggers של production של הצוות משתמשים ב-**structured logging**:

```js
console.log({
  event: "trigger_fired",
  triggerName: "nightlyPull",
  startedAt: new Date().toISOString(),
});

console.error({
  event: "row_write_failed",
  row: 17,
  buyer: "Yoav Cohen",
  vertical: "Car Deals PR",
  error: e.toString(),
});
```

`console.log` והחברים מקבלים object literal ומרנדרים אותו כ-JSON ב-Cloud Logging. ה-filter `jsonPayload.event="row_write_failed"` אז מציף כל רשומת failed-row על פני כל הריצות של החודש שעבר. ניתן לחיפוש, למיון, לחיבור. שרשור מחרוזות פשוט לא נותן לכם שום דבר מזה.

ה-Executions panel מציג את אותם logs מרונדרים יפה (הוא מבין את מבנה ה-JSON). Cloud Logging מציג אותם כשדות ניתנים-לחיפוש. בכל מקרה, הצורה המובנית משתלמת.

## מציאת ריצה ספציפית

כל ריצה של Apps Script מקבלת **execution ID**. רואים אותו ב-Executions panel ויכולים לחפש ב-Cloud Logging לפיו (`labels."script.googleapis.com/script_id" = "..."`). שני המקרים שזה חשוב:

- **משתמש מדווח "משהו השתבש ב-3 אחר הצהריים".** פותחים Executions, ממיינים לפי timestamp, מוצאים את הריצה של 3 אחר הצהריים, לוחצים פנימה, רואים את ה-logs. אין ניחושים.
- **דיווח באג מפנה ללינק של Cloud Logging.** הלינק מקודד את ה-script ID ואת חלון ה-timestamp. פותחים, ה-logs הרלוונטיים מסוננים מראש.

בלי execution IDs, דיבאג של trigger שיורה 100 פעמים ביום הוא ציד אחר מחט אחת בערימה של מחטים.

## שמירת logs

Cloud Logging שומר entries ל-**30 ימים** כברירת מחדל ב-project בתשלום, **7 ימים** ב-free tier. bug שמובחן ביום שני ליום שישי כושל כנראה איבד את ההקשר של יום שישי. ה-pattern שהצוות משתמש בו:

- שגיאות קריטיות נכתבות ל-tab "Run log" ב-meta-spreadsheet דרך `SpreadsheetApp.openById(...).getSheetByName("Run log").appendRow([...])`. שמירה קבועה, ניתן לשאילתה מ-dashboard.
- ה-entries של Cloud Logging נשארים כמקור האמת ל-stack traces ולזמני ריצה.

ה-meta-spreadsheet הוא read-only לצוות ו-append-only ל-trigger handlers. מבלים חצי שעה בהקמה פעם אחת, חוסכים שעות רבות של ארכיאולוגיה "מה קרה שבוע שעבר".

## נפוץ בשטח

- **trigger לילי עטוף ב-try/catch.** לכל handler trigger בבעלות הצוות יש את אותה צורה: לנסות את העבודה, לתפוס כל exception, לרשום אותו עם `console.error`, לשלוח מייל לצוות אם הכשל קריטי. בלי שלב המייל, trigger שבור פשוט ממשיך לנסות שוב לילית ולצבור ספירת שגיאות ב-Executions-tab שאף אחד לא שם לב.
- **ספירות שגיאות פר-buyer נמשכות ל-dashboard.** Cloud Logging ניתן לשאילתה מ-BigQuery (export בלחיצה אחת מ-console של Cloud Logging). הצוות מריץ query יומי שסופר `jsonPayload.event="row_write_failed"` מקובץ לפי `jsonPayload.buyer` וכותב את התוצאה ל-tab "Buyer errors" של ה-dashboard של ה-ops. ה-query לוקח 10 שניות; הנראות קבועה.
- **משך ריצת trigger כמטריקה.** כל trigger רושם `console.log({ event: "trigger_done", durationMs: Date.now() - startedAt })` בסוף. כש-Taboola pull הלילי מתחיל לקחת 5 דקות במקום 30 שניות, המטריקה מסמנת את זה לפני שה-timeout של 6 דקות יהרוג את הריצה.

## מלכודות מקצועיות

- **`console.log(spend)` כש-spend הוא object מדפיס "[object Object]".** או עוטפים עם `JSON.stringify(spend)` או מעבירים את ה-object literal כארגומנט (`console.log({ spend })`) כך ש-Cloud Logging שומר על המבנה.
- **`Logger.log("buyer=", buyer, " spend=", spend)` לא עושה multi-arg.** הוא משרשר עם פסיקים. תוצאה: `"buyer=,Yoav Cohen, spend=,412.5"`. משתמשים ב-`console.log("buyer=" + buyer + " spend=" + spend)` או פשוט `console.log({ buyer, spend })`.
- **שגיאות לא תפוסות ב-installable triggers מנפחות את ה-trigger error log.** Apps Script שומר מונה שגיאות פנימי פר-trigger. handler אחד מיושן שזורק כל לילה צובר 100+ שגיאות בחודש ו-Google בסופו של דבר שולחת לבעל ה-script מייל "ה-trigger שלך כל הזמן נכשל". עוטפים installable triggers ב-try/catch גם אם העבודה טריוויאלית.
- **השמירה של 7 ימים עוקצת באגים של יום שישי.** כשל ב-17:00 יום שישי נעלם עד 17:00 ביום שישי הבא. אם זמן התגובה של הצוות לבאג הוא "נסתכל ביום שני", איבדתם שלושה ימים של מרווח. כותבים שגיאות קריטיות לגיליון log קבוע גם.
- **Stackdriver ו-Cloud Logging הם אותו מוצר.** Google שינתה לו שם ב-2019. תשובות ישנות ב-StackOverflow, posts ישנים ב-Medium, ו-docs פנימיים ישנים עדיין אומרים "Stackdriver". אותו דבר.
- **Cloud Logging חינמי עד 50 GiB לפרויקט בחודש, ואז $0.50/GiB נכנס.** צוות שכותב 200 שורות log מובנות לריצה, על trigger שיורה כל שעה, הוא בערך 1.5 GiB/חודש. נוח חינמי. צוות שרושם את כל ה-row payload בכל row write יכול לעבור 50 GiB; מבנים את ה-logs כך שאתם רושמים מה שצריך, לא הכל.
- **`e.stack` לא תמיד נוכח.** חלק מהערכים שנזרקים אינם Error objects (למשל, `throw "boom"`); אין להם שדה `.stack`. רושמים `e.toString()` תמיד; רושמים `e.stack` הגנתית (`if (e.stack) console.error(e.stack);`).
- **try/catch שבולע את ה-exception בשקט גרוע מאשר אין try/catch.** `catch (e) { /* nothing */ }` מסיר את שגיאת ה-runtime וגם מסיר כל אות שמשהו השתבש. תמיד רושמים בתוך catch, גם אם העבודה לא קריטית.
