# ספריות ו-deployments ב-Apps Script: HEAD מול versioned, שיתוף בין פרויקטים

עד עכשיו כל Apps Script project היה עצמאי. ה-custom function חי ב-bound script, התפריט חי ב-bound script, ה-trigger חי ב-bound script. זה תקין ל-workbook אחד. זה מתפרק ברגע שלשלושה workbooks יש לכל אחד עותק משלהם של `normalizeBuyer` ולאחד מהם יש גרסה מיושנת. **ספריות** הן הדרך של Apps Script לתת לכם לכתוב חתיכת קוד פעם אחת ולייבא אותה לכל מקום. בשילוב עם **deployments** (משטח ה-versioning), הן הדרך שבה הצוות שומר על מקור אמת יחיד ל-utilities משותפים על פני תריסר workbooks.

השיעור הזה מכסה ארבעה דברים: מה ספרייה היא בעצם (project Apps Script עצמאי עם scriptId ידוע), איך לייבא אחת (manifest + userSymbol), הטרייד-אוף של HEAD מול versioned (שאלת המשמעת המרכזית), וזרימת ה-deployment שמכת גרסאות. ה-`SheetsLib` של הצוות הוא הדוגמה הקנונית לכל אורך הדרך: ספרייה משותפת של מנרמלים ו-bucketers שכל workbook מייבא תחת `userSymbol: "Shared"`.

## מהי ספרייה בעצם

ספרייה היא Apps Script project עצמאי: *לא* מקושר לאף spreadsheet: שה-functions שלו יכולים להיקרא על ידי projects אחרים. ה-project שמארח את ה-functions מזוהה על ידי **scriptId** (המחרוזת הארוכה ב-URL שלו). כל Apps Script project אחר יכול להצהיר על dependency על ה-scriptId הזה ב-manifest שלו, ומשם והלאה ה-functions של הספרייה הופכות נגישות תחת alias שנבחר.

באופן קונקרטי, בצד הספרייה:

```js
// ב-"SheetsLib" project עצמאי: scriptId "1abc..."
function normalizeBuyer(name) {
  return name.trim().replace(/\s+/g, " ").toLowerCase();
}

function countryToRegion(iso2) {
  const map = { US: "NA", CA: "NA", DE: "EU", FR: "EU", BR: "LATAM" /* ... */ };
  return map[iso2.toUpperCase()] ?? "OTHER";
}

function roiBucket(roi) {
  if (roi < 0.7) return "loss";
  if (roi < 1.1) return "flat";
  if (roi < 2.0) return "profitable";
  return "hero";
}
```

ה-project הזה מתפרסם כ-deployment (עוד על זה למטה), וה-workbooks האחרים של הצוות מייבאים אותו.

## ייבוא ספרייה

הספרייה מופיעה בשני מקומות: ב-manifest של ה-project ובקוד המקור שמשתמש בה. ה-manifest מצהיר על ה-dependency:

```json
{
  "timeZone": "America/New_York",
  "dependencies": {
    "libraries": [{
      "userSymbol": "Shared",
      "libraryId": "1abc...placeholder",
      "version": "3",
      "developmentMode": false
    }]
  }
}
```

ארבעת השדות:

| שדה | מה זה עושה |
|---|---|
| `userSymbol` | ה-alias המקומי שתשתמשו בו כדי לקרוא ל-functions. `"Shared"` אומר `Shared.normalizeBuyer(...)` במקור שלכם. חייב להיות JS identifier חוקי. |
| `libraryId` | ה-scriptId של ה-project של הספרייה (המחרוזת הארוכה מה-URL שלה). |
| `version` | מספר גרסה מקובע (`"1"`, `"2"`, `"3"`). Apps Script מקדם את זה כל פעם שמחבר הספרייה מפרסם deployment חדש. |
| `developmentMode` | כש-`true`, כל קריאה פוגעת ב-HEAD של הספרייה (קוד אחרון לא שמור) במקום בגרסה המקובעת. שימושי בזמן פיתוח של הספרייה; מסוכן ב-production. |

המקור משתמש ב-symbol:

```js
function tagRows() {
  const sheet = SpreadsheetApp.getActive().getSheetByName("Campaigns");
  const rows = sheet.getRange("B2:E61").getValues();
  const out = rows.map((row) => [
    Shared.normalizeBuyer(row[0]),       // קורא לספרייה
    row[1],
    row[2],
    Shared.countryToRegion(row[3]),       // קורא לספרייה
  ]);
  sheet.getRange("F2:I61").setValues(out);
}
```

Apps Script פותר את `Shared.*` בזמן הרצה על ידי הבאת גרסת `"3"` שפורסמה של הספרייה (לפי ה-manifest) וקריאה אליה. בפעם הראשונה, הצרכן מתבקש לכל OAuth scopes שהספרייה צריכה: `Shared.normalizeBuyer` הוא JS טהור אז לא מוסיף אף אחד, אבל function של ספרייה ששולחת מייל או פוגעת ב-Drive תרחיב את רשימת ה-scopes של הצרכן בזמן ההתקנה.

## HEAD מול versioned (הטרייד-אוף המרכזי)

לספריות Apps Script יש שתי דרכים לפתור לקוד אמיתי:

- **HEAD** (`developmentMode: true`): הצרכן תמיד מריץ את הקוד הלא-שמור הנוכחי של הספרייה. נוח בזמן שאתם מתקדמים, כי הצרכן קולט את העריכות שלכם ברגע שאתם שומרים את הספרייה.
- **Versioned** (`developmentMode: false`, `version: "N"`): הצרכן מריץ את ה-snapshot שמחבר הספרייה פרסם כ-version N. מחבר הספרייה יכול להמשיך לערוך באופן חופשי; שום דבר שהצרכן מריץ לא משתנה עד שהצרכן מקדם את `version` ל-`"N+1"`.

הכלל של הצוות: כל workbook של צוות מקבע גרסה. לכל ספרייה משותפת יש deployment לכל גרסה שעדיין בשימוש. קידום גרסה של ספרייה הוא פעולה מכוונת: מפרסמים deployment חדש, מחליטים אילו workbooks מקדמים קודם, ויכולים לחזור על ידי החלפת `version` של workbook חזרה.

`developmentMode: true` קיים לבדיקה של מחבר הספרייה. זו **אף פעם לא ההגדרה הנכונה בצרכן production.** workbook ב-`developmentMode: true` re-fetches את ה-HEAD של הספרייה בכל קריאה, מה שמאיט משמעותית את ההרצה, ומחבר הספרייה יכול לשבור כל צרכן בשמירה אחת רעה.

## Deployments: פרסום snapshot

deployment הוא איך שמכים גרסה. מתוך עורך Apps Script של הספרייה:

1. Deploy then New deployment.
2. Type: **Library**. (deployments של web app ו-Add-on הם קטגוריה שונה: שיעור 13 מכסה deployments של web app.)
3. Description: כותבים מה השתנה מאז הגרסה הקודמת ("Added `roiBucket`. Renamed `normalize` to `normalizeBuyer`."). התיאור מופיע ב-dropdown של הגרסה לצרכנים.
4. לוחצים Deploy. Apps Script מקצה גרסה שלמה ונועל את הקוד הנוכחי כתוכן של אותה גרסה.

צרכנים שמעדכנים את `version` של ה-manifest שלהם למספר החדש קולטים את הקוד החדש. צרכנים בגרסאות ישנות יותר ממשיכים להריץ את הקוד הישן ללא שינוי. שתי הגרסאות קיימות כל זמן ש-project הספרייה קיים.

## מציאת scriptId של ספרייה

ה-URL של הספרייה בעורך Apps Script נראה כמו `script.google.com/u/0/home/projects/1abc.../edit`. הקטע האמצעי הוא ה-scriptId. צרכנים של ספרייה מדביקים את ה-scriptId הזה לשדה `libraryId` של ה-manifest שלהם, או משתמשים ב-dialog Resources then Libraries של העורך (שכותב את אותו JSON בשבילכם).

## עכשיו לעבודה אמיתית

הקובץ ההתחלתי `Lesson.gs` מצהיר על `callSharedHelper()` כ-stub. יש לכם שתי משימות:

1. **עריכת ה-appsscript manifest** כדי להוסיף dependency של ספרייה. הצורה:
   ```json
   {
     "timeZone": "America/New_York",
     "dependencies": {
       "libraries": [{
         "userSymbol": "Shared",
         "libraryId": "1abc...placeholder",
         "version": "1",
         "developmentMode": false
       }]
     }
   }
   ```
   ה-`libraryId` הוא placeholder: אנחנו לא באמת מחברים ספרייה אמיתית לשיעור הזה. ה-grader בודק את ה*צורה* ושה-`userSymbol` הוא שם אמיתי (לא "placeholder" או "YOUR_SYMBOL").

2. **החלפת ה-body של `callSharedHelper`** כדי לקרוא ל-function על ה-`userSymbol` שבחרתם:
   ```js
   function callSharedHelper() {
     return Shared.normalizeBuyer("Yoav Cohen");
   }
   ```
   מה שהקלדתם בשדה `userSymbol` של ה-manifest חייב להתאים ל-prefix במקור שלכם. אם השתמשתם ב-`"Utils"` ב-manifest, ה-body חייב לקרוא ל-`Utils.something(...)`.

ה-grader עושה צילוב לשני הקבצים. עורכים אחד בלי השני וה-rules יגידו לכם בדיוק איזה צד לא בסדר.

## נפוץ בשטח

הדוגמה הדגלית של הצוות היא **`SheetsLib`**: project Apps Script עצמאי בבעלות חשבון Google של ה-head buyer, משותף עם הקבוצה של הצוות. הוא מייצא:

- `normalizeBuyer(name)`: מסיר whitespace ומאחד casing.
- `normalizeVertical(name)`: מבטיח את הסיומת ` PR`, מקצץ, מתקן casing.
- `countryToRegion(iso2)`: `"DE"` ל-`"EU"`, `"US"` ל-`"NA"`, וכו'. טבלה של 200 שורות שחיה במקום אחד.
- `roiBucket(roi)`: `"loss"`, `"flat"`, `"profitable"`, `"hero"`.
- `parseAdtechCampaignName(name)`: מפצל את שמות הקמפיין המובנים של הצוות לחלקיהם הסמנטיים.

כל workbook של הצוות: ה-Aggregator, ה-raws פר-פלטפורמה, ה-dashboards: מייבא את `SheetsLib` תחת `userSymbol: "Shared"`. כשרשימת המדינות צריכה לגדול (אזור חדש משיק), ה-head buyer עורך את `countryToRegion`, שולח גרסה חדשה (`"4"` ל-`"5"`), ועושה ping לצוות. כל בעלים של workbook מקדם את שדה `version` שלו בקצב שלו. ביום שישי כולם על גרסה 5; ה-rollout היה מסודר, כל צרכן רשם את הקידום, וחזרה אם משהו נשבר היא שינוי מספר אחד ב-manifest.

## מלכודות מקצועיות

- **עריכת הספרייה לא מעדכנת את הצרכנים עד ששולחים deployment חדש.** ספריות Apps Script אינן חיות כברירת מחדל: הקיבוע של הגרסה מקפיא את הקוד. שינוי ב-`countryToRegion` בעורך הספרייה שלא נפרס בלתי-נראה לכל צרכן בגרסה מקובעת. Deploy then New deployment, בכל פעם.
- **`developmentMode: true` ב-production.** זה עובד בהתחלה, ואז זה מפסיק. קריאות לוקחות יותר זמן באופן מורגש (הספרייה fetches HEAD בכל פעם), וברגע שמחבר הספרייה שומר refactor חצי-גמור, כל צרכן מתפרק. השתמשו ב-HEAD רק ב-workbook הבדיקה של מחבר הספרייה.
- **תלויות מעגליות של ספריות.** Project A מייבא B, B מייבא A. Apps Script ייתן לכם לשמור את שני ה-manifests אבל הקריאה תיכשל ב-runtime עם שגיאת פתרון קריפטית. שומרים על גרף ה-dependency כעץ.
- **הרחבת scope של ספרייה.** ייבוא של ספרייה שמשתמשת ב-`DriveApp` מוסיף את ה-scope של Drive להרשאה של *הפרויקט שלכם*. צרכנים רואים את זה במסך ה-consent כ-"ה-script הזה רוצה גישת Drive" גם אם הקוד שלהם לא נוגע ב-Drive. עורכים ביקורת על ה-scopes של הספרייה שלכם לפני שיתוף נרחב: ספרייה שעושה רק string manipulation לא צריכה לבקש scopes של Calendar או Gmail.
- **שינוי שובר בספרייה יכול לשבור את כל הצרכנים בבת אחת.** אם כולם רצים HEAD או שמחבר הספרייה כופה עדכון של כל צרכן לגרסה החדשה, rename אחד של function מיוצאת מוריד את כל ה-workbooks של הצוות בו-זמנית. המשמעת היא: שולחים את ה-function החדשה תחת השם החדש, שומרים את השם הישן כ-alias דק לגרסה אחת, מוחקים את ה-alias בגרסה N+2. זו אותה משמעת שמחבר ספרייה מתרגל בכל package ecosystem.
- **ה-`userSymbol` הוא בחירה של הצרכן, לא של מחבר הספרייה.** שני workbooks יכולים לייבא את אותה ספרייה תחת symbols שונים (`Shared` מול `Utils`). זה מותר אבל זה הופך snippets משותפים בין workbooks למבלבלים: בוחרים symbol אחד כצוות ומשתמשים בו בכל מקום.
- **function של ספרייה שקוראת ל-`SpreadsheetApp.getActiveSpreadsheet()` מחזירה את ה-spreadsheet הפעיל של הצרכן, לא של הספרייה.** זה מה שאתם רוצים רוב הזמן, אבל בפעם הראשונה שאתם כותבים ספרייה אתם עשויים להניח שזה מחזיר "איפה שקוד הספרייה חי", שזה project עצמאי בלי spreadsheet פעיל. מעבירים IDs ו-ranges ל-functions של ספרייה במקום להסתמך על context של active-sheet.
- **קנס ביצועים פר-קריאה לספרייה.** כל הפעלה של `Shared.normalizeBuyer(...)` חוצה גבול project; בסדר גודל של אלפיות שנייה פר-קריאה. בתוך לולאה הדוקה על 50,000 שורות זה 30+ שניות. ל-hot paths, משכפלים את ה-function הקטנה ל-project הצרכן ומסתמכים על הספרייה רק עבור המקור הקנוני.
