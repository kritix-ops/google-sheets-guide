# Quotas ו-batching: לגרום ל-Apps Script לשרוד נתונים אמיתיים

כל קריאה של Apps Script ל-service של Google היא round-trip ברשת. ה-script שלכם חי על תשתית של Google, ה-spreadsheet חי על תשתית של Google, ו-`getValue()` על F2 עדיין עובר את שכבת ה-RPC הפנימית שלהם. קריאה אחת על תא אחד מסתיימת במספר מילישניות ולא שמים לב. אותו קוד בלולאה על 5,000 שורות מסתיים בחמש דקות, אם הוא בכלל מסיים לפני שה-timeout של 6 דקות הורג אותו. התיקון הוא **batching**: מצמצמים את הקריאות התא-תא לקריאת range אחת ולכתיבת range אחת. ה-pattern מופיע בכל מקום (Sheets, Drive, Gmail, UrlFetchApp) וזה ה-lever הביצועי הגדול ביותר ש-Apps Script מציע.

השיעור הזה מכסה את עלות ה-round-trips עם מספרים מדידים, את חוקי הצורה הדו-ממדית שעוקצים כל חדש ל-`setValues`, את אותו רעיון batching המיושם ל-Drive ו-UrlFetchApp, את המכסות הקשות (timeout, מגבלות יומיות, קצב פר-דקה), ואת ה-primitives התומכים (`flush`, `sleep`, `LockService`, `fetchAll`). אחרי השיעור הזה, ה-patterns של `SpreadsheetApp` משיעור 4 וה-patterns של `UrlFetchApp` משיעור 11 שניהם מורכבים ל-scripts שמטפלים ב-workloads של 100,000 שורות בלי להזיע.

## עלות round-trip

פותחים את ה-Executions panel של עורך Apps Script, מריצים את הצורה הנאיבית על 100 שורות:

```js
function nightlyNaive() {
  const sheet = SpreadsheetApp.getActiveSpreadsheet().getSheetByName("Campaigns");
  for (let row = 2; row <= 101; row++) {
    const spend = sheet.getRange(row, 6).getValue();
    sheet.getRange(row, 10).setValue(spend * 3.7);
  }
}
```

זה 200 round-trips: 100 קריאות, 100 כתיבות. כל אחת היא כמה עשרות מילישניות. סה"כ: ~6 שניות. עכשיו דמיינו את אותו קוד על האגרגטור החודשי של 5,000 שורות: 10,000 round-trips, ~5 דקות. על הארכיון השנתי של 50,000 שורות: הרבה מעבר למכסה הצרכנית של 6 דקות, וה-script נכשל באמצע הלולאה עם השורות שהוא לא הגיע אליהן עדיין ריקות.

הצורה ב-batch:

```js
function nightlyBatched() {
  const sheet = SpreadsheetApp.getActiveSpreadsheet().getSheetByName("Campaigns");
  const spend = sheet.getRange("F2:F101").getValues();         // קריאה אחת
  const ils = spend.map(row => [row[0] * 3.7]);                 // צד JS, חינם
  sheet.getRange("J2:J101").setValues(ils);                    // כתיבה אחת
}
```

שני round-trips, בלי קשר לכמות השורות. עבודת 5,000 השורות שלקחה 5 דקות עכשיו לוקחת 3 שניות. עבודת 50,000 השורות שעשתה timeout עכשיו לוקחת 30 שניות. אותה לוגיקה, שני שינויים: `getValues` במקום לולאה של `getValue`, `setValues` של מערך דו-ממדי במקום לולאה של `setValue`.

## צורת ה-2D שעוקצת

`getValues()` תמיד מחזיר מערך דו-ממדי, אפילו לעמודות יחידות. עבור `F2:F101` תקבלו:

```
[[412.5], [285.3], [612.0], [187.25], ...]
```

100 מערכים פנימיים, כל אחד עם איבר אחד. ההגעה ל-spend בשורה 2 היא `values[0][0]`, לא `values[0]`. ה-map שממיר ל-ILS חייב להחזיר את אותה צורה:

```js
const ils = spend.map(row => [row[0] * 3.7]);
//                            ^^^^^^^^^^^^^^
//                            שימו לב לסוגריים העוטפים [].
```

לומד שכותב `spend.map(row => row[0] * 3.7)` מקבל מערך חד-ממדי (`[1526.25, 1055.61, ...]`) ו-`setValues` זורק:

```
Exception: The number of rows in the data does not match the number of rows in the range.
```

זו הטעות הנפוצה ביותר של batching. חוק הצורה: **`setValues` מצפה למערך דו-ממדי באותה צורה כמו ה-range.** כתיבה של עמודה יחידה היא `[[x], [y], [z]]`. כתיבה של שורה יחידה היא `[[x, y, z]]`. כתיבה של תא יחיד היא `[[x]]` (או פשוט משתמשים ב-`setValue` לתא אחד).

## Drive ושירותים אחרים עוקבים אחר אותו pattern

ה-script של שינוי שמות verticals של הצוות נהג לעשות את זה:

```js
const folder = DriveApp.getFolderById(FOLDER_ID);
for (const oldName of OLD_NAMES) {
  const file = folder.getFilesByName(oldName).next();         // round-trip לקובץ
  file.setName(file.getName().replace(" pr", " PR"));          // עוד אחד
}
```

10 קבצים = 20 round-trips. הגרסה ב-batch עוברת על התיקייה פעם אחת:

```js
const folder = DriveApp.getFolderById(FOLDER_ID);
const files = folder.getFiles();                                // iterator אחד
const toRename = [];
while (files.hasNext()) {
  const f = files.next();
  if (f.getName().endsWith(" pr")) toRename.push(f);
}
toRename.forEach(f => f.setName(f.getName().replace(" pr", " PR")));
```

ה-iterator עושה paging פנימי; קריאת רשת אחת מכסה ~100 קבצים. עבור תיקייה של 50 קבצים זה עכשיו 2 round-trips במקום 100.

ל-UrlFetchApp יש primitive batch משלו: `UrlFetchApp.fetchAll([req1, req2, req3])` מריץ requests במקביל ומחזיר מערך responses. עבור 30 fetches של endpoint זה חותך את wall-clock time פי 10.

## מכסות לדעת

ה-docs של Apps Script מפרטים את המכסות הקשות. אלה שעוקצים את הצוות:

| מכסה | Consumer (gmail.com) | Workspace |
|---|---|---|
| זמן ריצה פר ריצה | 6 דקות | 30 דקות |
| קריאות URL Fetch ליום | 20,000 | 100,000 |
| גודל URL Fetch payload | 50 MB | 50 MB |
| נמעני מייל ליום | 100 | 1,500 |
| Triggers פר script פר משתמש | 20 | 20 |
| קריאות Properties / Cache לדקה | (לא מתועד, אבל מוגבל) | (אותו דבר) |

השניים שעוקצים קודם:

- **timeout של 6 דקות (חשבונות consumer).** ה-pattern פר-תא פוגע בזה על כל דבר מעל ~5,000 שורות. ה-pattern ב-batch לא.
- **20,000 קריאות UrlFetchApp/יום ב-consumer.** trigger שמושך נתונים פר-קמפיין עם קריאה אחת לשורה, רץ פר שעה, עובר את זה ביום רגיל. משתמשים ב-`fetchAll` ועושים batch של ה-requests upstream.

עדין: אין מכסה מתועדת על `SpreadsheetApp.getRange().getValue()` לדקה, אבל בפועל שכבת ה-round-trip מגבילה סביב 600-1,000 קריאות/דקה. מעבר לזה, קריאות מתחילות לחסום, וטיימר ההרצה ממשיך לתקתק נגד תקציב 6 הדקות.

## כלי batching אחרים

כמה primitives שמתחברים ל-pattern ה-batch:

- **`SpreadsheetApp.flush()`** מאלץ כל כתיבה בתור להתחייב מיד. שימושי כשקריאה במורד צריכה לראות את הכתיבות (`setValues(...); flush(); getValues(...);`). Apps Script בדרך כלל עושה batch לכתיבות באופן אופורטוניסטי; `flush` עושה את התפר מפורש.
- **`Utilities.sleep(ms)`** להכנסת הפסקות מכוונות בין bursts. UrlFetchApp מגביל ב-~600/דקה; `sleep(100)` בין batches של 10 שומר אתכם מתחת למגבלת הקצב על pulls ארוכים.
- **`LockService.getScriptLock()`** כששני triggers יכולים לרוץ באותו זמן ולהתחרות על אותו range. ה-lock עושה להם serialize כך שהכתיבות ב-batch לא יתערבבו.
- **`fetchAll([{url, method, headers}, ...])`** לקריאות UrlFetch מקביליות. כל המערך יורה במקביל; מערך ה-response שומר על סדר.

## נפוץ בשטח

- **Nightly Taboola pull, refactored.** ה-script המקורי כתב 5,000 שורות תא בכל פעם ולקח 20 דקות (ולפעמים timeout). refactored לקריאת `setValues` אחת עם מערך דו-ממדי של 5,000 שורות, הוא מסיים תוך 30 שניות. אותה לוגיקה, שתי קריאות API במקום 5,000.
- **מסלול המיגרציה מ-`IMPORTRANGE` ל-Apps Script** (שיעור 1.27 מכסה את החלופה החיה). כשה-sheet upstream יש לו 50,000 שורות ו-`IMPORTRANGE` גורם ל-dashboard לקחת 90 שניות להיפתח, הצוות עובר ל-pull יומי של Apps Script: `Sheets.Spreadsheets.values.get` (או `SpreadsheetApp.openById(...)`) פעם אחת על המקור, `setValues` אחד למראה המקומית, ה-dashboard קורא מהמקומית. מחליף טריות בזמן אמת (שלא הייתה ל-`IMPORTRANGE` באמת בכל מקרה) ל-load מיידי.
- **Trigger פר-buyer ששולח roll-up במייל.** קורא את כל ה-tab `Campaigns` פעם אחת, מחשב סכומים פר-buyer ב-JS, כותב ל-tab dashboard בבת אחת, ואז שולח מייל אחד פר-buyer (עם `UrlFetchApp.fetchAll` אם ה-API של buyer-portal צריך הודעה גם). כל הזרימה לוקחת 4 שניות עבור 8 buyers; הגרסה פר-תא לקחה 90 שניות.

## מלכודות מקצועיות

- **`setValues` מצפה למערכים דו-ממדיים אפילו עבור כתיבות של עמודה יחידה.** `[[x], [y], [z]]`, לא `[x, y, z]`. הודעת השגיאה מצביעה על ספירת שורות, מה ששולח לומדים לרדוף אחרי bug של ספירת שורות כשהטעות האמיתית היא הצורה.
- **off-by-one כשגודל ה-range לא תואם למערך.** `getRange("J2:J60").setValues(arr60Rows)` זורק כי ה-range הוא 59 שורות. תואמים את ספירת השורות בדיוק או משתמשים ב-`getRange(2, 10, arr.length, arr[0].length)` כדי לגודל את ה-range מהמערך עצמו.
- **`SpreadsheetApp.flush()` הוא לפעמים נושא משא.** trigger שכותב ואז מיד קורא את אותו range יכול לראות את הערכים הישנים כי הכתיבה עדיין בתור. `flush()` ביניהם גורם לקריאה לראות את הכתיבה. בדרך כלל מיותר; כשזה חשוב, הסימפטום הוא bug לסירוגין מסוג "זה לא יכול להיות אפשרי".
- **ערבוב קריאות batch ופר-תא מבטל את החיסכון.** `getValues` אחד ואז לולאת `for` עם `setValue` לכל שורה היא אותה עלות של 60 round-trips כמו המקורי. או batch מלא בשני הצדדים או לא בכלל.
- **Triggers שעושים timeout באמצע כתיבה משאירים נתונים חלקיים.** כשכתיבה של 5,000 שורות עושה timeout בנקודת 6 הדקות, השורות שהתחייבו לפני ה-timeout נשארות; השאר לא. ריצה הבאה רואה sheet לא עקבי. עוטפים batches גדולים ב-try/catch וכותבים סימן "last completed row" כך שריצות חוזרות יכולות לחזור.
- **`UrlFetchApp.fetch` בלולאה פוגע ב-throttle של 600/דקה.** משתמשים ב-`fetchAll` ל-requests מקביליים, או `Utilities.sleep(100)` בין bursts כדי להישאר מתחת למגבלת הקצב על pulls ארוכים. שגיאת ה-throttle שקטה; הקריאה פשוט חוסמת יותר ויותר זמן עד שטיימר ההרצה הורג את הריצה.
- **לחץ זיכרון על קריאות `getValues` ענקיות.** קריאה של 100,000 שורות × 20 עמודות זה 2 מיליון תאים, ~50 MB של זיכרון JS. Apps Script לא מתעד מגבלה קשה אבל בפועל scripts יכולים לעשות OOM. עבור datasets גדולים מאוד, מחלקים את הקריאה לבלוקים של 10,000 שורות ומעבדים כל אחד בזה.
- **`setValues` על ranges מוגנים read-only נכשל בשקט** (שיעור 2.7 מכסה הגנת טווח לעומת הגנת גיליון). אם חלק מה-range היעד מוגן, `setValues` או זורק או מדלג על התאים המוגנים, תלוי בהגדרת "warning only" של ההגנה. תמיד מאשרים את ההגנה ב-tab היעד לפני כתיבה גדולה.
