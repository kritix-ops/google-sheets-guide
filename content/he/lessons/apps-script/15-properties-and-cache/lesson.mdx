# PropertiesService ו-CacheService: אחסון קבוע ואחסון קצר-טווח

Apps Script רץ ב-sandbox בלי disk מקומי. כל מה שה-script שלכם רוצה לזכור בין ריצות חייב לחיות איפשהו ש-Google מנהלת. שני ה-surfaces לזה הם **`PropertiesService`** (אחסון key/value עמיד שנשאר לתמיד) ו-**`CacheService`** (אחסון מהיר קצר-טווח שמתפנה אחרי שש שעות לכל היותר). כל trigger ב-production שהצוות כותב משתמש באחד או באחר: API tokens ב-Properties כך שה-trigger לא ישלח אותם במקור, שער החליפין היומי ב-Cache כך ש-200 תאים לא יפגעו כולם ב-FX API.

השיעור הזה מכסה את שלושת ה-scopes ששני השירותים חושפים (Script, Document, User), משטח ה-API ב-60 שניות, ה-pattern של קריאה תלת-שכבתית שכל trigger של הצוות משתמש בו, מגבלות הגודל ששווה לזכור, הכלל "Properties אינו לסודות", וה-LockService ששומר על writers מקבילים מלהיכנס למרוץ. עד הסוף תוכלו בביטחון לאחסן כל דבר משער FX של 5 bytes לרשימת buyer של 200 שורות.

## שלושה scopes, שני שירותים

שני השירותים חושפים את אותם שלושה scopes:

| Scope | מה משותף | משתמשים בשביל |
|---|---|---|
| **Script** | כל המשתמשים של ה-script project הזה. | config של כל הצוות: endpoints של API, טבלאות שערים ברירת מחדל, ה-ID של תיקיית Drive שאליה הולכים exports. |
| **Document** | ה-script הזה מקושר ל-spreadsheet הזה. קבצים שונים מקבלים stores נפרדים. | state ספציפי ל-workbook: timestamps של רענון אחרון, שער ה-FX הקנוני לתקופת הדיווח של הקובץ הזה. |
| **User** | המשתמש הנוכחי. חברי צוות שונים מקבלים stores נפרדים. | העדפות פר-משתמש: איזו תצוגת dashboard מישהו ברירת מחדל, ה-API token האישי שלו. |

ה-getters משקפים את שמות ה-scope:

```js
const scriptProps = PropertiesService.getScriptProperties();
const docProps    = PropertiesService.getDocumentProperties();
const userProps   = PropertiesService.getUserProperties();

const scriptCache = CacheService.getScriptCache();
const docCache    = CacheService.getDocumentCache();
const userCache   = CacheService.getUserCache();
```

בוחרים את ה-scope שמתאים למחזור החיים של הנתונים. הבחירה הלא נכונה היא ה-bug שעוקץ שלושה חודשים מאוחר יותר כש"מסיבה כלשהי" מאיה רואה שער אחד ויואב רואה אחר.

## שני השירותים ב-60 שניות

```js
// PropertiesService: עמיד, write-and-forget.
const props = PropertiesService.getDocumentProperties();
props.setProperty("usdIlsRate", "3.72");        // הערכים חייבים להיות מחרוזות
const rate = props.getProperty("usdIlsRate");    // מחזיר "3.72" או null

// CacheService: קצר-טווח, TTL ב-שניות.
const cache = CacheService.getDocumentCache();
cache.put("usdIlsRate", "3.72", 3600);           // פג תוקף בעוד שעה
const cached = cache.get("usdIlsRate");           // מחזיר "3.72" או null
```

שלושה פרטים שעוקצים:

- **ערכי Properties הם מחרוזות.** `setProperty` ממיר מה שאתם מעבירים למחרוזת. `getProperty` מחזיר את המחרוזת. אתם מנתחים אותה חזרה למספר / boolean / JSON בעצמכם.
- **TTL של Cache הוא ב-שניות, לא במילישניות.** `cache.put(k, v, 60)` חי לדקה. `cache.put(k, v, 60000)` חי לזמן ה-cache המקסימלי (שש שעות, מוגבל); ה-function לא זורקת וה-bug צץ רק כשפריטים נעלמים מוקדם מדי או מאוחר מדי.
- **שניהם `get` ו-`getProperty` מחזירים `null` על miss.** תמיד בודקים `null` לפני קריאה ל-`.length` או חשבון על הערך.

## ה-pattern התלת-שכבתי

ה-pattern שכל trigger של הצוות משתמש בו ל"השג את שער ה-FX":

```js
function getOrFetchRate() {
  const cache = CacheService.getDocumentCache();
  const cached = cache.get("usdIlsRate");
  if (cached !== null) return Number(cached);

  const props = PropertiesService.getDocumentProperties();
  const stored = props.getProperty("usdIlsRate");
  if (stored !== null) {
    cache.put("usdIlsRate", stored, 3600);
    return Number(stored);
  }

  return 3.7;
}
```

קוראים top to bottom: cache קודם (חיפוש ברמת מיקרו-שנייה), Properties שני (כמה אלפיות שנייה, עמיד), ברירת מחדל אחרון (ה-function עדיין עובדת ביום הראשון כשעדיין לא נכתב כלום). כש-Properties פוגע, ה-function מחממת את ה-cache כך שהקריאה הבאה תוך השעה היא cache hit. כל קריאה מחזירה מספר; הקורא לא צריך להתעסק במקרה null.

הצורה הזו מכלילה. מחליפים "rate" ב-"API token", "buyer list", "last refresh", כל ערך שאתם מאחזרים שוב ושוב. העלות של שכחת שכבה אחת היא trigger איטי. העלות של שכחת שכבה שלוש היא `TypeError: cannot convert null to number`.

## מגבלות ששווה לזכור

| Surface | מגבלה פר-ערך | מגבלה כוללת | TTL |
|---|---|---|---|
| ערך Properties | 9 KB | 500 KB לכל property store | לתמיד |
| ערך Cache | 100 KB | (לא מתועד) | מקסימום 6 שעות |

מלכודת נפוצה: זריקת JSON blob גדול ל-Properties. ה-"רשימת buyer פעילה" של הצוות גדלה מ-8 שמות ל-240 על פני שנתיים; הקוד המקורי עשה `props.setProperty("buyers", JSON.stringify(list))` ויום אחד בשקט קיצץ באמצע מחרוזת. התיקון הוא פיצול למספר מפתחות (`buyers_chunk_0`, `buyers_chunk_1`) או מעבר לקובץ Drive המופנה לפי ID. Properties הוא config store, לא database.

ערכי Cache יכולים להיות גדולים יותר (100 KB) אבל הם מתפנים על זמן ועל לחץ זיכרון. ערך cache בגודל CSV קטן בסדר; בגודל של dataset שלם לא.

## Properties אינו לסודות

כל מי שיכול לערוך את ה-bound script יכול לקרוא כל מפתח ב-`getScriptProperties` וב-`getDocumentProperties`. המחרוזת `Authorization: Bearer XYZ123` חיה בטקסט פשוט. אם הסוד דולף, ה-API מאחוריו חשוף.

לסודות אמיתיים הצוות משתמש ב-Google Cloud Secret Manager, מאוחזר ב-runtime דרך `UrlFetchApp.fetch` עם service-account token. ההקמה הזו מוגזמת ל-dashboard לפי צוות בלי PII, אבל זו הצורה הנכונה ברגע ש-API key אמיתי מעורב. Properties הוא ל**config שלא צריך להיות מוסתר**: endpoints, IDs של sheets, שער ה-FX.

## Writers מקבילים מתחרים

שני triggers שרצים באותו זמן שניהם קוראים ל-`setProperty` על אותו מפתח. כתיבה אחת מנצחת; השנייה בשקט נדרסת. עבור נתונים "last-write-wins" (שער ה-FX האחרון) זה בסדר. עבור counters שמתקדמים-באחד ורשימות בסגנון append זה bug של אובדן נתונים.

התיקון הוא `LockService.getScriptLock()`:

```js
const lock = LockService.getScriptLock();
lock.waitLock(5000);
try {
  const props = PropertiesService.getScriptProperties();
  const current = Number(props.getProperty("runCount") || 0);
  props.setProperty("runCount", String(current + 1));
} finally {
  lock.releaseLock();
}
```

שני triggers יכולים שניהם לנסות לתפוס את ה-lock; אחד מחכה עד חמש שניות שהשני ישחרר. הקידום עכשיו בטוח. אותו pattern של lock עובד ל-Cache, ל-spreadsheet עצמו, או לכל store משותף אחר.

הקובץ ההתחלתי `Lesson.gs` מצהיר על `function getOrFetchRate()` עם body ריק. מיישמים את ה-pattern התלת-שכבתי:

2. קוראים את `PropertiesService.getDocumentProperties()`. אם `"usdIlsRate"` שם, מחממים את ה-cache (TTL של שעה) ומחזירים אותו כמספר.

## נפוץ בשטח

- **API tokens ב-script properties.** ה-Taboola pull trigger של הצוות קורא את ה-API key שלו עם `PropertiesService.getScriptProperties().getProperty("TABOOLA_TOKEN")` ומשתמש בו ב-`Authorization` header. סיבוב המפתח הוא עדכון של שורה אחת דרך **Project Settings** של העורך (אייקון גלגל ברצועת השמאל) **then Script Properties then Add script property**; ללא שינוי קוד. שימו לב שרק Script Properties יש להן UI; Document Properties ו-User Properties מוגדרות מהקוד בלבד.
- **שער FX יומי ב-cache ליום.** ה-trigger של הבוקר מאחזר את השער מ-API של הבנק הלאומי, כותב אותו ל-Properties (עמיד, שורד פינוי cache), ומחמם את ה-cache לשעה. כל קריאה ל-`=usdToILS(F2, getOrFetchRate())` על פני ה-workbook במהלך היום היא אז cache hit.
- **העדפות dashboard פר-משתמש.** כשה-sidebar מאפשר למשתמש להחליף בין תצוגות "by buyer" ו-"by vertical", הבחירה הולכת ל-`UserProperties` כך שפתיחה מחדש של ה-sidebar מחר ממשיכה מאיפה שעצרו.
- **timestamp של רענון אחרון של ה-workbook המקושר.** `DocumentProperties.setProperty("lastRefresh", new Date().toISOString())` בסוף כל pull מוצלח. ה-sidebar קורא אותו ומציג "Refreshed 4 minutes ago" כך שהצוות בוטח שה-dashboard לא מיושן.

## מלכודות מקצועיות

- **התייחסות ל-Properties כאחסון סודות.** כל מי שיש לו גישת עריכה ל-script project יכול לקרוא כל מפתח. סודות אמיתיים (API tokens שמעניקים גישה לנתונים, PII של לקוחות) שייכים ל-Google Cloud Secret Manager, לא ל-Properties. השימוש של "API token" בסדר כשה-API פנימי וה-script מאחורי workspace SSO; זה לא בסדר ל-API key ציבורי.
- **TTL של CacheService במילישניות.** טעות נפוצה שמועברת מעולם ה-JS. הארגומנט השלישי ל-`cache.put` הוא **שניות**. `cache.put(k, v, 60 * 60 * 1000)` לא נכשל. הוא מוגבל למקסימום של 6 שעות, וה-bug מציג כ-"ה-cache נשאר הרבה יותר זמן ממה שציפיתי."
- **בלבול בין "אין ערך" ל-"פג תוקף" על cache misses.** שניהם מחזירים `null`. אי אפשר לדעת מערך ההחזרה אם המפתח אף פעם לא נכתב או שהוא נכתב ואז התפנה. אם הלוגיקה שלכם צריכה להבחין (נדיר), הבדיקה השנייה מול Properties היא מה שאומר לכם.
- **המגבלה של 9 KB פר-property מקצצת בשקט.** Properties שומר blobs של JSON-stringified בלי תלונה; ארוכים נחתכים באמצע מחרוזת ופירוק ה-JSON בדרך חזרה נכשל. עבור כל דבר שיכול לגדול (רשימת buyers, log של עריכות אחרונות), משתמשים בקובץ Drive המופנה לפי ID וקוראים אותו דרך `DriveApp.getFileById(id).getBlob().getDataAsString()`.
- **Writers מקבילים שמאבדים increments.** שני triggers שכותבים את אותו counter בלי `LockService` ישחררו בשקט אחת מהכתיבות. הקורא התלת-שכבתי של השיעור הוא read-only ובטוח; ברגע שאתם מתחילים לכתוב חזרה, עוטפים את הכתיבה ב-`LockService.getScriptLock()`.
- **שכחה להמיר ערכי Properties חזרה לסוג.** `props.getProperty("usdIlsRate")` מחזיר את המחרוזת `"3.7"`, לא את המספר `3.7`. `+rate` או `Number(rate)` עושה את ההמרה. דילוג עליה והכפל במורד עושה חזרה של מחרוזת (`"3.7" * 412.5` למספר, במקרה, כי JS) או גרוע יותר, במקרי קצה, NaN.
- **`deleteAllProperties()` לא מוחק את ה-property store.** הוא רק מנקה את הערכים; ה-store עדיין קיים, getProperty מחזיר null לכל דבר. אין דרך למחוק את ה-property store עצמו עבור project script נתון.
- **Cache מחזיר ערכים מיושנים אחרי setProperty.** Cache הוא read-through, לא write-through. כתיבה ל-Properties *לא* מבטלת את ה-cache. אם אתם כותבים ערך חדש ל-Properties, אתם חייבים או `cache.remove(key)` או לחכות ל-TTL.
