# Simple triggers: onOpen, onEdit, onSelectionChange

Custom functions רצות רק כשתא מבקש מהן. הצעד הבא הוא קוד שרץ על *event* של גיליון: משתמש פותח את ה-spreadsheet, עורך תא, בוחר טווח אחר. Apps Script מטפל בזה דרך קבוצה קטנה של **שמות functions שמורים**. אם מצהירים על function ברמה העליונה עם אחד מהשמות האלה, ה-runtime מפעיל אותה אוטומטית בכל פעם שה-event המתאים קורה: בלי רישום, בלי הגדרה. אלה ה-**simple triggers**.

השיעור הזה מכסה ארבעה שמות trigger, את ה-event object שכל אחד מקבל, את ה-auth context הצר שתחתיו הם רצים, ואת המקרים שבהם פונים לאחד מול האחר. משטח ה-simple-trigger קטן אבל הוא נושא בערך 70% ממה ש-workbook אמיתי עושה מחוץ ללחיצות תפריט ידניות: חתימה אוטומטית של העורך, נרמול של נתונים כשהם נוחתים, בניית התפריט בפתיחה. שיעור 8 מכסה installable triggers, שזה איך שעוקפים את מגבלות ה-auth context.

ארבעת השמות השמורים שחשובים:

| שם | מופעל כש |
|---|---|
| `onOpen(e)` | ה-workbook נפתח על ידי משתמש עם גישת עריכה. |
| `onEdit(e)` | משתמש עורך תא (paste, type-in, fill-down, delete). |
| `onSelectionChange(e)` | הבחירה הפעילה זזה לתא או טווח אחר. |
| `onChange(e)` | שינוי מבני: הוספת שורה, שינוי שם של sheet, עריכת פורמט, וכו'. |

שני דברים לשים לב אליהם מראש. **השמות רגישים לרישיות.** `onedit` לא מופעל. `OnEdit` לא מופעל. רק `onEdit` מופעל. ו**ה-function חייבת להיות ברמה העליונה**: אותו כלל כמו ב-custom functions. הצהרה מקוננת או arrow שמוצמד ל-const בלתי נראים למערכת ה-trigger.

## הערה על `onOpen` בקורס הזה

ה-bound Apps Script project של הקורס הזה כבר מצהיר על `function onOpen()`: זה מה שמתקין את **תפריט Lesson** כשפותחים את ה-workbook. אתם לא יכולים להצהיר על `onOpen` שני באותו project; Apps Script יסרב לשמור. הקטע המעשי שלכם בשיעור הזה מתמקד ב-`onEdit` במקום. ב-workbook שבבעלותכם, `onOpen` הוא שלכם לכתוב. ה-pattern זהה ל-`onEdit`: מצהירים עליו ברמת ה-top, עושים משהו עם `e`, מחזירים.

## ה-event object

כל simple trigger מקבל event object: לפי מוסכמה בשם `e`. הצורה משתנה מעט מ-trigger ל-trigger; השדות הרלוונטיים ל-`onEdit` הם:

```js
function onEdit(e) {
  e.range;     // Range object: התא או הטווח שנערכו
  e.value;     // הערך החדש (עריכות תא יחיד בלבד; undefined אחרת)
  e.oldValue;  // הערך הקודם (עריכות תא יחיד בלבד)
  e.user;      // בדרך כלל ריק ב-onEdit פשוט. לפי docs ה-events של Google
               // הוא מאוכלס רק "אם זמין (תלוי בקבוצה מורכבת של הגבלות
               // אבטחה)" — בפועל זה אומר שהעורך הוא בעל ה-script, או
               // שה-script מקושר למסמך Workspace עם מדיניות admin
               // מתאימה. אל תסתמכו על e.user.getEmail() לזיהוי חברי
               // צוות; ראו את הקטע המודגש לפני הדוגמה המעובדת ושיעור 8
               // לתיקון של installable-trigger.
  e.source;    // ה-Spreadsheet object שבו העריכה קרתה
}
```

ה-`range` הוא השדה הכי שימושי: הוא נושא את ה-sheet, את השורה, את העמודה ואת הכתובת A1 הכל ביחד. pattern של בדיקת הגנה טיפוסי קורא אותו קודם:

```js
function onEdit(e) {
  const range = e.range;
  if (range.getSheet().getName() !== "Campaigns") return;
  if (range.getColumn() !== 6) return; // F = Spend
  // מכאן והלאה, אנחנו יודעים שהעריכה נחתה בעמודת Spend ב-Campaigns.
}
```

ל-`onChange` יש צורת event שונה: אין `range`, אין `value`, במקום זה יש שדה `changeType` עם ערכים כמו `"INSERT_ROW"`, `"REMOVE_COLUMN"`, `"FORMAT"`. אל תעתיקו body של `onEdit` ל-`onChange` ותצפו שזה יתקמפל לכם.

## מגבלת ה-auth context

simple triggers רצים **כמשתמש שהפעיל את ה-event**, ב-auth scope צר בכוונה. הם יכולים:

- לקרוא ולכתוב ל-spreadsheet הפעיל (`SpreadsheetApp.getActiveSpreadsheet()`)
- להשתמש ב-`Utilities.*` לפורמט ולפענוח
- להריץ JS טהור

הם **לא יכולים**:

- לשלוח מייל (`MailApp.sendEmail`, `GmailApp.sendEmail`)
- לפנות לרשת (`UrlFetchApp.fetch`)
- לגעת במסמכים אחרים (`SpreadsheetApp.openById`, `DriveApp.*`)
- להציג sidebar או dialog (ה-UI context הפעיל אינו שלהם לתבוע)
- לשנות הרשאות Drive
- לקרוא scripts חיצוניים

המלכודת היא שהקריאות האלה **נכשלות בשקט**: אין שגיאה שנזרקת, אין רשומת לוג, אין כלום ב-Execution dashboard. ה-trigger נראה כאילו הוא הופעל בסדר; המייל פשוט אף פעם לא יוצא. אם אתם מוצאים את עצמכם רוצים אחד מהשירותים המוגבלים, התשובה היא בשיעור הבא: **installable trigger**, רשום עם auth מלא.

ל-simple triggers יש גם **תקציב של 30 שניות**. עוברים בלולאה על 60,000 שורות בתוך `onEdit` וה-runtime הורג אותה באמצע הלולאה. שומרים את ה-handlers של simple-trigger קטנים.

## מתי כל trigger הוא הכלי הנכון

סיור קצר:

- **`onOpen`**: המקום היחיד האמין להתקין תפריט מותאם. workbook נפתח, תפריט מופיע. כל דבר יותר מורכב (גודל אוטומטי של שורות, צביעה מחדש של עמודת סטטוס) שייך ל-function שהתפריט *קורא לה*, לא ל-`onOpen` עצמו, כי מסלול הפתיחה נמצא במסלול הקריטי של טעינת ה-workbook.
- **`onEdit`**: סוס העבודה. משתמשים בו להיגיינת נתונים בשורה: מילוי אוטומטי של ה-buyer מהמייל של העורך כששורת קמפיין חדשה מופיעה, נרמול של שם vertical כשמקלידים, חתימה של זמן השינוי האחרון. נזהרים ממה שנחשב "עריכה": הקלדה בתא, fill-down, paste, delete, ו*הפעלת checkbox* כולם מפעילים אותו. paste המוני מפעיל אותו פעם אחת עם כל טווח ה-paste כ-`e.range`.
- **`onSelectionChange`**: מופעל בכל הקשה על מקש חץ. רק דברים זולים: עדכון של תא status bar, הדגשת השורה הפעילה. handler של 100ms כאן בסדר; של 500ms מרגיש לא יציב.
- **`onChange`**: מופעל על שינויים מבניים שהאחרים מפספסים. הגנה אוטומטית על שורת כותרת כשמישהו מוסיף עמודה. צפייה לשינויי שם sheet לא מכוונים ב-workbook שבו נוסחאות `IMPORTRANGE` (שיעור 1.27) תלויות בשמות tabs.

### דוגמה מעובדת: הגנה על שורת הכותרת כשמוסיפים עמודה

`onEdit` לא מופעל כש-buyer לוחץ קליק ימני על כותרת עמודה ובוחר "Insert 1 column left". התאים זזים; אף עריכה לא נחתה. `onChange` תופס את זה דרך `e.changeType`. קבוצת הערכים שהשדה מקבל קבועה: `INSERT_ROW`, `INSERT_COLUMN`, `REMOVE_ROW`, `REMOVE_COLUMN`, `INSERT_GRID` (tab חדש), `REMOVE_GRID` (tab נמחק), `FORMAT`, `EDIT`, `OTHER`. רוב ה-handlers מסננים את השניים-שלושה הסוגים שאכפת להם וחוזרים על כל השאר.

## קוראים את זה לפני שאתם פונים ל-`e.user`

`e.user.getEmail()` הוא השדה שכל לומד פונה אליו ראשון ("אני אמלא אוטומטית את ה-buyer ממי שערך את השורה"), והוא השדה שבשקט לא עובד. ה-documentation של ה-events של Google אומר ש-`e.user` מאוכלס "אם זמין (תלוי בקבוצה מורכבת של הגבלות אבטחה)". ב-trigger פשוט של `onEdit` זה מתורגם ל: **`e.user` בדרך כלל ריק עבור כולם חוץ מבעל ה-script**, פלוס קבוצה צרה של מקרים בדומיין Workspace שבהם מדיניות ה-admin מאפשרת את זה.

מה זה אומר בפועל:

- handler של `onEdit` פשוט שקורא ל-`e.user.getEmail()` יחזיר `""` עבור כל חבר צוות שאינו בעל ה-script. ה-handler נראה כאילו הוא עובד עבורכם בבדיקה (אתם הבעלים) ונשבר בשקט עבור שאר הצוות.
- trigger **installable** של `onEdit` (שיעור 8) רץ עם auth מלא, אבל הוא רץ כ-*מתקין*, לא כעורך. `e.user` ב-installable trigger אומר לכם מי התקין את ה-trigger, לא מי עשה את העריכה. אז installable triggers לא סוגרים גם הם את הפער הזה.
- המסלולים הכנים ל-"מי ערך את השורה הזו?" הם: (א) לדרוש הזנה ידנית של שם ה-buyer, (ב) להשתמש ב-dropdown שמקושר לרוסטר ה-buyer, או (ג) לתחזק installable trigger פר-משתמש שכותב את כתובת המייל של המתקין ל-bucket של user-properties וקורא אותה בזמן עריכה. אפשרות (ב) היא זו שהצוות באמת משתמש בה.

הדוגמה המעובדת למטה שומרת על הצורה של `e.user` בשביל ה-hook של השיעור (כך שתראו איך השדה אמור להיראות), אבל הסעיף של "נפוץ בשטח" שמתחתיו נכתב מחדש כדי לשקף את מה שבאמת נשלח לפרודקשן.

## נפוץ בשטח

שני patterns מ-workbooks האמיתיים של הצוות:

- **מילוי אוטומטי של ה-buyer מ-dropdown, לא מ-`e.user`.** עמודת Buyer ביומן היומי היא dropdown של data-validation שמקושר לגיליון של רוסטר ה-buyer הקנוני. handler של `onEdit` צופה בשורה לזיהוי Vertical חדש שהוקלד, ואם Buyer עדיין ריק, מגדיר את ה-validation של התא ל-"show warning" כך שה-buyer לא יוכל להמשיך בלי לבחור את עצמו. הצוות ניסה את ה-lookup של `e.user.getEmail()` פעם אחת; הוא נכשל בשקט עבור כל חבר צוות שאינו בעל ה-script, וה-dashboards התמלאו בייחוסי Buyer ריקים. ה-dropdown ניצח.
- **סימון אוטומטי של עמודת Spend כשנוגעים בה מחדש.** כש-buyer מכוונן מספר spend באמצע השבוע, `onEdit` חותם סימן "updated" קטן עמודה אחת לידו. הביקורת השבועית עושה pivot על העמודה הזו כדי לסמן שורות שזזו מההעלאה. ה-pattern הזה לא תלוי ב-`e.user`; הוא קורא רק את `e.range`, שתמיד מאוכלס. בגלל זה הוא שורד שם שה-pattern של buyer-from-email לא שורד.

הקובץ ההתחלתי `Lesson.gs` כבר מצהיר על `function onEdit(e)` עם body ריק. שלוש בדיקות שה-body צריך לעשות, לפי הסדר:

1. **בדיקת sheet.** אם `e.range.getSheet().getName()` אינו `"Campaigns"`, חוזרים מיד. בלי זה, ה-trigger יופעל בכל tab: כולל tabs עוזרים של ה-Sidebar וכל דבר אחר ב-workbook.
2. **בדיקת עמודה.** אם `e.range.getColumn()` אינו `6` (F היא העמודה ה-6), חוזרים. אנחנו רוצים שהסימן ייכתב רק על עריכות Spend, לא על כל עריכת תא בכל מקום בשורה.
3. **כותבים את הסימן.** משתמשים ב-`range.getSheet().getRange(range.getRow(), 10).setValue("updated")` כדי לכתוב `"updated"` לעמודה J של השורה שנערכה.

שומרים את הפרויקט. פותחים את tab Campaigns. עורכים את F2. J2 אמור להתמלא ב-`"updated"`. עורכים את F3. J3 מתמלא. עורכים תא אחר: J נשאר במקומו.

אם שום דבר לא קורה, פותחים את תצוגת ה-**Executions** ברצועת השמאל של Apps Script (אייקון השעון). כל הפעלה של simple-trigger מתועדת שם. גם הפעלה כושלת מתועדת שם. אם השורה חסרה לחלוטין, ה-trigger function לא נרשם: בדרך כלל typo בשם ה-function (O גדולה `OnEdit` הוא הנפוץ ביותר).

## מלכודות מקצועיות

- **`onEdit` מופעל בכל לחיצת מקש בעריכה בתוך תא.** הוא לא: אבל ה-`onSelectionChange` הקשור מופעל בכל לחיצה על מקש חץ כשהמשתמש זז סביב ה-sheet. אם אתם מחברים עבודה כבדה ל-selection-change, כל תזוזת סמן מריצה אותה.
- **paste המוני מפעיל את `onEdit` פעם אחת עם כל טווח ה-paste.** נוסחה שמניחה ש-`e.range` הוא תא יחיד קורסת על `e.value` שהוא `undefined`. תמיד בודקים `range.getNumRows() * range.getNumColumns() === 1` לפני קריאת `e.value` / `e.oldValue`.
- **ל-`onChange` יש צורת `e` שונה.** אין `e.range`, אין `e.value`. העתקת body של handler מ-`onEdit` ל-`onChange` וציפייה שזה יעבוד היא session של דיבאג של 20 דקות.
- **שמות שמורים רגישים לרישיות.** `function onedit` לא מופעל. `function OnEdit` לא מופעל. עורך Apps Script לא מזהיר אתכם.
- **ה-timeout של 30 שניות לא סולח.** אם ה-handler שלכם צריך לעבור על כל ה-sheet, זה הכלי הלא נכון: מתזמנים installable trigger מבוסס-זמן שרץ בלילה עם auth מלא ותקציב ארוך יותר.
- **simple triggers לא יכולים לשלוח מייל, fetch, או לגעת במסמכים אחרים.** הקריאה נכשלת בשקט. אם ה-handler שלכם "נראה לא עובד" ויש בו `MailApp.sendEmail` או `UrlFetchApp.fetch`, זו הסיבה. שדרגו ל-installable trigger בשיעור הבא.
- **`e.user.getEmail()` מחזיר מחרוזת ריקה עבור חברי צוות.** מכוסה בקטע המודגש מעל הדוגמה המעובדת: `e.user` מאוכלס באופן אמין רק כשהעורך הוא בעל ה-script (או, באופן צר, משתמש Workspace באותו דומיין שבו מדיניות ה-admin מאפשרת את זה). עבור כל חבר צוות אחר השדה ריק. ל-`Session.getActiveUser().getEmail()` יש את אותה הגבלה ב-context של simple-trigger, אז זה לא workaround. התיקון האמיתי הוא installable trigger (שיעור 8) פלוס dropdown לזהות העורך, לא heuristic.
- **onEdit handler שעורך באופן רקורסיבי את אותו range.** אם ה-handler עושה `range.setValue(x)` בפנים, הכתיבה הזו לא מפעילה `onEdit` שוב (ה-runtime של Google מגן מהלולאה), אבל כתיבה לתא *אחר* שיש לו נוסחה שמפנה לתא שנערך יכולה להיכנס למפל. צופים ב-Executions panel להפעלות חוזרות.
