## Goal

Make the Sheets Guide bilingual (English + Hebrew) with a header toggle the user can flip at any time. Hebrew must read like it was written by a native Israeli adtech professional — not translated. RTL must be correct everywhere, not patched on. The user lands on the same lesson when switching languages.

Success looks like: every English lesson has a Hebrew counterpart that an Israeli pro would actually want to read; the toggle works on every page; nothing in the UI looks broken in RTL; LTR code/formulas/cell refs render cleanly inside RTL prose.

```
content/

  assignments/                       # locale-neutral grading rules

      02-coming-from-excel.ts

  en/
    lessons/
      formulas/

        02-coming-from-excel/lesson.mdx
        ...
  he/
    lessons/
      formulas/
        01-grid-model/lesson.mdx     # NEW — Hebrew translation
        02-coming-from-excel/lesson.mdx
        ...

messages/                            # UI shell strings (header, buttons, errors)
  en.json
  he.json

lib/
  i18n/
    routing.ts                       # next-intl defineRouting
    navigation.ts                    # locale-aware Link, useRouter, etc.
    request.ts                       # next-intl getRequestConfig
    glossary.md                      # locked Hebrew terminology — single source of truth
  content/
    lessons.ts                       # updated to read from content/{locale}/lessons/...

app/
  [locale]/                          # NEW dynamic segment, wraps existing app
    (app)/                           # existing app group, moved inside [locale]
    sign-in/                         # moved inside [locale]
    layout.tsx                       # sets html lang + dir, mounts NextIntlClientProvider
    not-found.tsx
  layout.tsx                         # thin shell, no <html> tag here anymore
  globals.css

proxy.ts                             # composes existing auth check + next-intl middleware
```

**Why this shape:**
- **Datasets locale-neutral** because data names (buyers, verticals, platforms) stay English in both locales per the user's decision.
- **Assignments locale-neutral with keyed strings** because grading logic ("H1 must equal `=E5`") is the same in any language; only the `detail` text shown to the learner needs translation. Forking the rule code would invite drift.
- **Lessons split per locale** because they are 100% prose-driven content, not code. Translators (us, in this case) work on one MDX file at a time.
- **`messages/{locale}.json`** for UI shell strings (nav labels, button text, error toasts) — small payload, ICU-formatted for the few places we need plurals.
- **`[locale]` segment wraps `(app)`** so all existing routes inherit locale handling without rewriting their internals.

### Routing

- `lib/i18n/routing.ts` — `defineRouting({ locales: ['en', 'he'], defaultLocale: 'en' })`. No localized pathnames; lesson slugs are the same in both languages (e.g., `/en/lessons/formulas/01-grid-model` and `/he/lessons/formulas/01-grid-model`).
- `lib/i18n/navigation.ts` — `createNavigation(routing)` to export locale-aware `Link`, `useRouter`, `usePathname` for use across components.

### Middleware

`proxy.ts` is currently auth-only. After: compose auth + next-intl. Auth runs first (since it returns 401 for API or redirects to `/sign-in`), then next-intl handles locale detection/redirect for non-API requests.

### Layout & RTL

`app/[locale]/layout.tsx`:
- Sets `<html lang={locale} dir={locale === 'he' ? 'rtl' : 'ltr'}>` — at the `<html>` level, not body, so scrollbars/CSS logical properties work correctly.
- Loads `Heebo` via `next/font/google` (subsets: hebrew + latin) with `font-display: swap`.
- Mounts `NextIntlClientProvider` so client components can call `useTranslations`.

### Toggle UI

`components/locale-toggle.tsx` (new). Two-button segmented control: `EN | עב`. Uses `usePathname` and `useRouter` from `lib/i18n/navigation` to swap the locale prefix while staying on the same path. Lives in `components/top-bar.tsx`. Persists locale via cookie automatically (next-intl handles this) plus URL is the source of truth.

### Tailwind v4 RTL discipline

Project audit needed: any existing class with physical direction (`ml-`, `mr-`, `pl-`, `pr-`, `text-left`, `text-right`, `border-l`, `border-r`, `rounded-l-`, `rounded-r-`, `left-`, `right-`) gets swapped to its logical equivalent (`ms-`, `me-`, `ps-`, `pe-`, `text-start`, `text-end`, `border-s`, `border-e`, `rounded-s-`, `rounded-e-`, `start-`, `end-`).

Reserve `rtl:` / `ltr:` variants for things logical properties can't handle:
- Directional icons (chevrons, back arrows): `rtl:scale-x-[-1]` or per-icon mirroring
- Specific transforms or animations that need direction-specific values

`space-x-*` is a known gotcha — switch to `gap-*` with flex/grid or add `rtl:space-x-reverse`.

### Hebrew typography (per skills' guidance)

```css
/* in globals.css */
html[dir="rtl"] {
  font-family: 'Heebo', 'Assistant', 'Noto Sans Hebrew', sans-serif;
  line-height: 1.7;
  letter-spacing: normal;       /* NEVER add letter-spacing for Hebrew */
  word-spacing: 0.05em;
}
html[dir="rtl"] code,
html[dir="rtl"] pre,
html[dir="rtl"] .ltr {
  direction: ltr;
  unicode-bidi: isolate;
  font-family: 'Fira Code', 'Source Code Pro', monospace;
}
```

Inline code (`=$E$5`, cell refs like `B5`, formula names) inside Hebrew prose is wrapped in `<code>` (already MDX-default) and gets LTR direction via the CSS rule above. No per-occurrence `dir="ltr"` needed.

### Content-loading code update

`lib/content/lessons.ts` (existing file that loads MDX) needs to accept a `locale` parameter and resolve `content/{locale}/lessons/{track}/{slug}/lesson.mdx`. If the Hebrew file doesn't exist yet for a given lesson (mid-translation), fall back to English and surface a small "Hebrew translation in progress" badge in the UI — better UX than a 404.

### Assignment grading

`content/assignments/formulas/01-grid-model.ts` (new shape):

```ts
const details = {
  en: {
    h1Empty: "H1 is empty. Type `=E5` in H1 to reference Maya's Pet Insurance spend.",
    h1Wrong: (formula: string) => `H1 contains \`${formula}\`, not \`=E5\`. A relative reference has no \`$\` characters.`,
    // ...
  },
  he: {
    h1Empty: "התא H1 ריק. הקלד `=E5` ב-H1 כדי להפנות ל-spend של Maya ב-Pet Insurance.",

    // ...
  },
};
```

The grading runner picks the right `details` map based on the current locale.

## Translation discipline (governs every lesson)

All Hebrew prose follows these rules. They will live in `lib/i18n/glossary.md` so future translation passes stay consistent.

**Voice:**
- **Ktiv maleh** (full spelling with vav and yod) per Academy of the Hebrew Language standard. Example: תוכנה, not תכנה.
- **Business-casual register**, not formal/textbook Hebrew. The voice should feel like an experienced Israeli media buyer explaining things to a peer, not a manual.
- **Gender-neutral phrasing** where natural (`יש ללחוץ` over `אתה צריך ללחוץ`, `ניתן לבחור` over `אתה יכול לבחור`). When unavoidable, use plural masculine — Israeli tech default. Never use slash notation like משתמשים/ות in technical writing.
- **No literal idioms.** "Walks off the bottom" in Hebrew should be `יוצא מהטווח`, not a calque. "Source of broken formulas" → `סיבה שכיחה לשבירת נוסחאות`.

**What stays Latin (per user's "minimal translation" choice):**
- All function names: `VLOOKUP`, `XLOOKUP`, `ARRAYFORMULA`, `QUERY`, `LAMBDA`, `IMPORTRANGE`, etc.
- All formulas: `=$E$5`, `=F2-E2*$J$1`, `=ARRAYFORMULA(...)`.
- All cell addresses and ranges: `B5`, `E2:E13`, `J1`.
- All dataset names: buyer first names, vertical names ("Used Cars PR"), platforms (Taboola, Outbrain, Facebook, Google).
- Adtech jargon: ROI, CPC, EPC, CPM, CTR, vertical, campaign, media buyer, pixel, conversion.
- Sheets-specific UI labels referenced from the actual Google Sheets UI (e.g., "Named ranges", "Data validation") — these stay in English because that's what the learner sees in the product.

**What gets translated:**
- All explanatory prose.
- Headings.
- Quiz questions, options, and explanations (but answer keys reference English code/cells).
- "Used in the wild" and "Pro pitfalls" sections.
- Captions on interactive components.
- Error messages and feedback details.

**Glossary (preview — full list will be in `lib/i18n/glossary.md`):**

| English | Hebrew | Notes |
|---|---|---|
| spreadsheet | גיליון | full word; not "טבלה" (which means table) |
| workbook | חוברת עבודה | matches Sheets product term |
| sheet (tab) | גיליון | same word; context disambiguates |
| cell | תא | universal |
| range | טווח | universal |
| named range | טווח בעל שם | matches Sheets UI translation |
| formula | נוסחה | leave the formula text itself in Latin |
| reference | הפניה (when verb), reference (when as adtech term, leave Latin) | depends on context |
| absolute reference | reference מוחלט / הפניה מוחלטת | both readable |
| relative reference | reference יחסי / הפניה יחסית | both readable |
| pin / lock | לנעול | "ל-pin" sounds wrong in Hebrew |
| copy down (fill) | למלא למטה | not "להעתיק למטה" |
| volatile function | פונקציה תנודתית | technical term, established |
| recalculation | חישוב מחדש | universal |
| lookup table | טבלת lookup | hybrid; "טבלת חיפוש" feels translated |
| dashboard | dashboard | universal Hebrew tech usage |
| aggregation | אגרגציה | transliterated; "צבירה" feels academic |

The glossary file is treated as binding. New terms added during translation get appended there, not invented per lesson.

## Alternatives considered (and rejected)

**Alternative A — Parallel files in same folder (`lesson.mdx` + `lesson.he.mdx`)**
- Pro: smallest diff, easiest to see both versions side by side.
- Con: mixes locales in one folder, doesn't generalize cleanly to a third language later.
- **Rejected** because user picked top-level split.

**Alternative B — Single MDX with locale sections**
- Pro: one file per lesson.
- Con: requires a custom MDX parser, worst diffs, breaks every existing tool.
- **Rejected** as architecturally worst.

**Alternative C — Cookie-only locale (no URL change)**
- Pro: simpler routing.
- Con: can't share a Hebrew URL; back/forward broken; mid-stream language switches are jarring.
- **Rejected** as the wrong UX bar (CLAUDE.md rule 10).

**Alternative D — Maximally Hebrew voice**
- Pro: more "complete" translation feel.
- Con: doesn't match how Israeli tech professionals actually talk; reads stiff.
- **Rejected** by user (picked minimal translation).

**Alternative E — Hebrew buyer/vertical names**
- Pro: more immersive Hebrew reading.
- Con: forks the dataset, complicates grading messages, breaks " PR" team convention from CLAUDE.md.
- **Rejected** by user.

## Lazy-user walk-through (CLAUDE.md rule 10)

User opens `localhost:3000` for the first time:
- Lands on `/en/...`. Sees the English UI as before. **Toggle in top bar shows `EN | עב`** with EN highlighted.
- Clicks `עב`. URL changes to `/he/...`, page reloads in RTL, layout mirrors, Hebrew content appears, font swaps to Heebo seamlessly (no FOIT thanks to `font-display: swap`). They are on the same lesson.
- Refreshes the page. Still in Hebrew (URL is the source of truth).
- Bookmarks `/he/lessons/formulas/04-lookups`. Reopens later. Lands in Hebrew on the right lesson.
- Shares URL with a Hebrew-speaking colleague. Colleague opens it, sees Hebrew immediately.
- Opens a new tab to `localhost:3000/`. Redirected to `/en/` (default locale) because no cookie/URL hint says Hebrew. (We could detect Hebrew browser language in middleware later if desired — flagged as enhancement.)
- On mobile: toggle is in the same place (top bar collapses but keeps the toggle visible). Both languages render correctly at narrow widths.
- Hits back button after toggling: returns to previous URL in previous language. Browser history is honest.

Edge cases:
- A Hebrew lesson file doesn't exist yet (mid-Phase-2): user sees English content with a small "Hebrew translation in progress" badge; toggle still works; nothing 404s. We do not silently fail.
- Code blocks (`=$E$5`) inside Hebrew prose render LTR with monospace font, surrounded by Hebrew RTL prose. The bidi algorithm handles punctuation cleanly because we use `unicode-bidi: isolate` on `<code>`.
- Numbers (campaign IDs, prices) inside Hebrew prose render LTR by default (Unicode bidi handles digits) — no extra markup needed unless we see a specific issue.

## Decisions (resolved 2026-05-10)

1. **Default locale is user-configurable.** Account menu gets a "Default language" setting with two options (English / Hebrew). Saved to the `NEXT_LOCALE` cookie that next-intl already respects in middleware — no DB schema needed. On a truly first visit (no cookie set), the user lands on English; the first time they pick a default, the cookie is written and every subsequent root-level visit honors it.
2. **No browser-language auto-detection.** Confirmed — defer.
3. **Scroll position preserved across toggle.** Confirmed — switching mid-lesson should not lose place.
4. **No pre-architecture for a third language.** Confirmed — but the structure naturally supports it if needed later.

## Implementation note: default-language setting

The locale toggle in the top bar (`EN | עב`) controls the current view. The "Default language" setting in the account menu controls **what locale you land on** when you visit a root-level URL or revisit later. Two distinct concepts:

- **Toggle** — flips the current session URL from `/en/...` to `/he/...` or vice versa.
- **Default setting** — writes `NEXT_LOCALE` cookie. Affects: (a) future visits to `/` redirect to the preferred locale; (b) other locale-less URLs route through the preferred locale.

UI pattern: a small "When you open the app, start in: ⚪ English / ⚪ Hebrew" radio in the account menu dropdown. Saving updates the cookie immediately.
